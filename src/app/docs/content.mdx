# Documentation

Bitcoin meets Forth. Henceforth is a native iOS app that combines a Forth-2012 compliant interpreter with an integrated Bitcoin SV wallet — one stack-based language for arithmetic, scripting, and payments.

## Goals

### Achieved

- **Bitcoin (BSV) integration** — full wallet with HD key derivation (BIP-44 and Type42), transaction building, ARC broadcasting with failover, SPV verification, Paymail support, and 140+ Bitcoin Script opcodes including the Chronicle upgrade.
- **Block headers** — locally chain-linked header store anchored to a hardcoded checkpoint, auto-synced from chain tip on every launch via a WebSocket history stream. SPV Merkle proof verification is bounded to the chain-validated range — no silent network fallback for missing headers.
- **SwiftBSV** — fully integrated for transactions, Script building, BIP-32/39 key management, and ECDSA signing.
- **OPCodes** — all standard and Chronicle-restored opcodes available as FORTH words. Script Recording mode assembles Bitcoin Scripts from the terminal.
- **Files** — full CRUD for `.fs` and `.forth` files with iCloud backup. Script files identified by `SCRIPT-BEGIN` / `SCRIPT-END` markers.
- **Colour customisation** — foreground and background colour pickers, keyboard selection, and Dynamic Type support throughout.
- **Forth-2012 compliance** — 133 / 133 CORE words implemented, verified by the Hayes test suite.

### Get people coding

Provide a simple interface for the FORTH programming language, making it easy for people to learn to code.

### Future

- CRDT (Conflict-free Replicated Data Type) system using the timestamp server for user-defined words.
- Trigonometry and calculus extensions.

## Reference

Everything in FORTH is a **word** separated by spaces. That's all there is to the syntax. It's so simple.

> **FORTH is LIFO** — FORTH is a stack-based programming language which operates on a *Last In, First Out* principle.

Ideally we give the user just enough to make use of FORTH and through FORTH some of Swift's functionality such as networking requests, the timer built into Swift, etc. But not so much as to be relied upon — user creation of words should be encouraged.

### Compile Words

One of the great things about FORTH is its ability to extend the compiler during run time.

```
:           puts the user into compile mode where they can
            start to define their own word.
;           exits compile mode so that word interpretation
            can again occur.
recurse     calls the word being executed.
exit        exits the current word.
immediate   marks the most recently defined word as immediate,
            causing it to execute during compilation rather
            than being compiled.
postpone    forces compilation of the next word, even if it
            is marked IMMEDIATE.
value       (x --)  Creates a named value that can be read by
            name and changed with TO.  Usage: 42 value myval
to          (x --)  Change the value of a word created with
            VALUE.  Usage: 99 to myval
does>       ( -- )  Defines the runtime behaviour of a CREATE'd
            word. Everything after DOES> runs when the created
            word is executed, with the data-field address on
            the stack.
include     ( -- )  Loads and runs a FORTH file.
            Usage: include maths.fs
```

### Double-Cell Arithmetic

Double-cell words operate on 64-bit values represented as two stack items (high cell on top). Required by the Forth-2012 CORE standard for intermediate precision.

```

m*       (n1 n2 -- d)    Signed multiply, double-cell result.

                         negative infinity.
sm/rem   (d n1 -- n2 n3) Symmetric division; quotient rounds toward
                         zero.
um/mod   (ud u1 -- u2 u3) Unsigned division.
```

### Transaction Builder

The transaction builder words allow programmatic construction of Bitcoin transactions directly from the FORTH terminal. Build a transaction step by step, then broadcast it.

```
tx-new           ( -- )  Initialise a new transaction builder.
tx-set-fee       (n -- ) Set fee rate in satoshis per kilobyte.
                         Usage: 500 tx-set-fee
tx-add-output    (n -- ) Add P2PKH output; expects amount on
                         stack and address as next word.
                         Usage: 1000 tx-add-output 1A1zP1...
tx-add-data      ( -- )  Add OP_RETURN data output.
tx-preview-toggle ( -- ) Toggle preview mode. When ON,
                         TX-BROADCAST shows without sending.
tx-show          ( -- )  Display current transaction.
tx-clear         ( -- )  Clear builder.
tx-broadcast     ( -- )  Build, sign, broadcast via ARC.

send             ( amount c-addr u -- )
                 Standard payment in a single word. Validates,
                 then presents PayView with the amount + address
                 pre-filled. The user long-presses to confirm;
                 Face ID gates the actual broadcast via ARC.
                 Terminal output on success: "sent TXID: <id>".
                 Usage: 1000 s" 1A1zP1..." send

send-many        ( amount1 ... amountN c-addr u -- )
                 Multi-recipient payment with per-recipient
                 amounts. Pops the address string first to
                 derive N, then pops N amounts. Presents
                 MultiPaySheet for review before Face ID.
                 Atomic: any validation failure rejects the
                 whole transaction.
                 Usage: 1000 5000 250 s" 1A 1B 1C" send-many
```

> **Standard payment example.** Single recipient:
> ```
> 1000 s" 1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa" send
> ```
> Multiple recipients, equal-split, 2500 sats each:
> ```
> 5000 s" 1A1zP1... 1BvBMS..." send
> ```

> **Multi-recipient with per-recipient amounts.** When recipients should receive *different* amounts, use `send-many`. The recipient count is derived from the address string (single count source of truth) and the function pops exactly that many amounts.
>
> Reading rule for both `send` and `send-many`: amounts come first, the recipient string comes last. This places the address string at the top of the stack so `send-many` can read it first and infer N before consuming the amount block — no explicit count parameter is needed.

#### Standard Transaction Script

Every installation includes a `standard-transaction.fs` file in the Files tab. This is a Bitcoin Script file that defines the OP_RETURN output attached to your payments. It is automatically loaded each time you open the Pay view.

```
( Standard Transaction Script )

SCRIPT-BEGIN
OP_FALSE OP_RETURN
." Hello, you are welcome." >data data>script
SCRIPT-END
```

`SCRIPT-BEGIN` activates script recording; `OP_FALSE OP_RETURN` emits the opcodes for a data-carrying output; `."` places the message on terminal output; `>data` converts it to raw bytes on the data stack; `data>script` emits those bytes as PUSHDATA into the script buffer; `SCRIPT-END` finalises.

### BAP Identity

BAP (Bitcoin Attestation Protocol) provides a decentralised identity system built on Bitcoin. Identity keys are derived using Type42 (BRC-42) key derivation from the wallet's master key.

```
bap-id       ( -- )      Show the BAP identity key + signing address.
bap-sign     ( -- )      Sign with BAP identity key.
                         Usage: bap-sign <message>
bap-verify   ( -- flag)  Verify a BAP-signed message.
                         Usage: bap-verify <addr> <sig> <message>
bap-register ( -- )      Build a BAP ID registration tx (OP_RETURN
                         with BAP + AIP attestation).
```

> **AIP signatures are over raw message bytes, not hex.** `bap-sign` and the AIP attestation inside `bap-register` apply the Bitcoin Signed Message wire format directly to raw payload bytes. Signatures produced by current builds verify against any BAP / AIP implementation that follows the standard (including `@bsv/sdk`).

### Script Recording

Script recording is a macro assembler for Bitcoin Script. When recording is active, `op_*` words emit their opcodes into a script buffer rather than executing. Standard FORTH control flow still runs normally.

```
script-begin   Start recording. op_* words emit opcodes to the
               script buffer. FORTH control flow still runs.
script-end     Stop and finalise; displays compiled script hex.
script-show    Display the current buffer as hex.
script-clear   Discard buffer; stop recording.
script-use     Set recorded script as the selected transaction
               script (for building transactions).
script-save    Save current script with a name.
               Usage: script-save <name>
script-load    Load a saved script by name.
               Usage: script-load <name>
script-list    List all saved scripts.
```

> **Raw bytes require a `0x` prefix during recording.** A bare hex-looking token like `ff` is parsed according to current `BASE` and pushed to the integer stack. To emit raw opcode bytes, use an explicit `0x`-prefixed literal (e.g. `0xdeadbeef`).

### Script Bridge Words

The bridge words connect FORTH's stacks to the script recording buffer, enabling dynamic script construction with computed values, strings, and file data.

```
>script       (n -- )  Emit integer as a Bitcoin Script number.
data>script   ( -- )   Emit top of data stack as PUSHDATA. Use
                       after crypto ops to inject computed hashes.
text>script   ( -- )   Convert following token to UTF-8 bytes and
                       emit as PUSHDATA.
                       Usage: text>script image/jpeg
file>script   ( -- )   Read a file's raw contents and emit as
                       PUSHDATA. For uploading images, videos, or
                       data on-chain.
                       Usage: file>script photo.jpg
```

### Script Helper Words

Pre-built script templates for common Bitcoin transaction patterns.

```
make-p2pkh-script     Create a P2PKH locking script from an address.
make-opreturn-script  Create OP_RETURN output script from data.
make-2of3-multisig    Create 2-of-3 multisig script from three pubkeys.
script-pushdata       Push raw bytes via OP_PUSHDATA.
```

> **Example: upload an image to the blockchain via the B:// protocol.**
> ```
> script-begin
>   op_false op_return
>   text>script 19HxigV4QyBv3tHpQVcUEQyq1pzZVdoAut
>   file>script photo.jpg
>   text>script image/jpeg
>   text>script binary
>   text>script my_photo
> script-end
> script-use
> pay
> ```

> **Example: build a hash-locked script with a computed HASH160.**
> ```
> script-begin
>   op_dup op_hash160
>   " secret" op_sha256 op_hash160
>   data>script
>   op_equalverify op_checksig
> script-end
> ```

## Bitcoin Wallet

Henceforth includes a full Bitcoin SV (BSV) wallet, enabling users to create wallets, receive and send transactions, and interact with the blockchain — all from the same app that runs FORTH programs.

### Wallet Architecture

The wallet is built on a hierarchical deterministic (HD) key structure, meaning a single seed phrase generates an unlimited number of addresses.

- **Seed Phrase** — a 12-word BIP-39 mnemonic generated when creating a new wallet. The master backup: from it, every key can be regenerated.
- **Key Derivation** — two derivation methods are supported:
  - **Type42 (BRC-42)** — the default for new wallets. Uses elliptic curve key tweaking (private key addition, public key multiplication) for more flexible derivation paths.
  - **BIP-44** — the legacy standard. Retained for restoring wallets created by other software. Uses the standard path `m/44'/236'/0'/0/n`.
- **Address Rotation** — after each transaction, a new receiving address is derived automatically. Improves privacy by avoiding address reuse.

> **Security.** Private keys and seed phrases are stored exclusively in the iOS Keychain, protected by the device's Secure Enclave. They never leave the device and are never transmitted over the network.

#### Address Discovery

The wallet discovers addresses with funds using a shared Type42 scanner (`scanType42Addresses`). The scanner is *derivationType-independent* — it always tries Type42 first if the master key exists in Keychain, regardless of what `derivationType` says on the wallet card. This prevents funds from becoming invisible if the derivation type metadata is wrong.

- **Dynamic scan range** — scans at least 20 addresses (gap limit) past the last address with activity, with a minimum floor of 50 addresses.
- **Receive and change chains** — scans both `1-wallet-{N}` (receive) and `0-change-{N}` (change) invoice numbers.
- **BIP-44 fallback** — after Type42, scans standard BIP-44 paths. A wallet can have funds on both derivation paths.
- **Auto-repair** — if Type42 addresses are discovered but `derivationType` is wrong, the scanner automatically corrects it and persists the fix.

### Wallet Cards

Each wallet is represented by a *Wallet Card* in the app interface. A card stores:

- **Wallet title** — a user-chosen name.
- **Main address** — the primary receiving address.
- **Derived addresses** — additional addresses generated through key rotation.
- **Balance** — confirmed and unconfirmed satoshis, reconciled from the UTXO set.
- **Derivation type** — Type42 or BIP-44.

Multiple wallets can be created and managed simultaneously. Biometric (Face ID / Touch ID) authentication is required to access sensitive details.

#### Default Wallet

One wallet can be marked as the *default wallet*, indicated by a star on the wallet card. The default wallet is used by the terminal `send` word and other non-UI operations. To change the default wallet, open the wallet details view and tap **Set as Default Wallet**. The setting persists across app launches.

### Transactions

#### Receiving

To receive BSV, share your wallet's receiving address or scan its QR code. The wallet monitors for incoming transactions using:

1. **JungleBus REST polling** — polls every 30 seconds for new transactions via `GET /v1/address/get/{address}`. When a new transaction ID is detected, the wallet triggers an automatic refresh.
2. **Periodic sync** — full balance and UTXO refresh as a safety net.

When a new transaction is detected, the wallet automatically refreshes balance, UTXOs, and transaction history.

#### Notifications

The wallet uses a UTXO-based deposit detection system. Instead of comparing balances (which can fluctuate mid-sync), it tracks known UTXO outpoints (`txHash:txPos`) per wallet in UserDefaults. Only genuinely new outpoints trigger a notification — the system is immune to confirmation state changes and mid-sync transient balances.

When a wallet is first seen, existing outpoints are seeded silently (no "received entire balance" notification on first install).

#### Sending

Transactions are built locally on the device:

1. **UTXO Selection** — the wallet selects unspent transaction outputs to fund the payment, avoiding ordinal-protected UTXOs.
2. **Fee Calculation** — fees are calculated using the current rate from the preferred miner (GorillaPool or TAAL) via ARC policy endpoints.
3. **Change Output** — any excess is returned to a fresh change address derived from the wallet.
4. **Signing** — each input is signed with the correct private key for its address (Type42 or BIP-44 derived).
5. **Anti-Fee-Sniping** — the `nLockTime` field is set to the current block height, preventing miners from re-mining old transactions for higher fees.
6. **Broadcasting** — the signed transaction is submitted via ARC with automatic failover between GorillaPool and TAAL.

The `pay` word in the FORTH terminal opens the transaction builder. The pay view has three tabs:

- **OP_RETURN** — write a text message to embed on-chain.
- **Script** — select a saved script or a `.fs` script file.
- **Upload** — pick a photo, video, or file from the device and upload it on-chain via the B:// protocol.

#### Terminal Send Words

In addition to `pay`, two terminal words compose payments directly from the stack:

- **`send`** — `( amount c-addr u -- )`. Example: `1000 s" 1A..." send` sends 1000 satoshis to the given address. Space-separated addresses in the string equally split the amount.
- **`send-many`** — `( amount1 ... amountN c-addr u -- )`. Example: `1000 5000 250 s" 1A 1B 1C" send-many` sends 1000, 5000, and 250 satoshis to three recipients in one transaction.

Both accept P2PKH addresses only — paymail aliases must be resolved through the single-recipient `send` flow first.

> **Mandatory pre-signing review.** Neither word broadcasts directly. `send` pre-fills the existing pay view; `send-many` presents a **MultiPaySheet** with a scrollable grid showing each (recipient, amount) row plus the total. The user sees the exact output set before the long-press triggers signature. The single canonical confirmation line `sent TXID: <id>` appears on the terminal after broadcast success.

#### Fragmentation-Aware Selection

UTXO selection switches to a *fragmentation-aware* policy when the wallet has more than 100 UTXOs OR when the average UTXO value is below 5000 satoshis with more than 40 UTXOs. In this mode:

- The dust-input cap rises from 10 to 50, draining more of the dust pile per send.
- Regular UTXO sort flips from largest-first to smallest-first.
- Smart-change splitting is *disabled* — the residual coalesces into a single primary change output instead of re-fragmenting.
- A transaction-size ceiling refuses to assemble a transaction larger than `maxStandardTxSize` (100 KB) *before* biometric prompts.

The user initiates an ordinary send; the wallet consolidates as a side effect. No separate "Consolidate" button needed.

> **Smart Sync.** When a payment is initiated, UTXOs are loaded from the local disk cache first (instant). A network fetch only occurs on genuine first launch when no UTXO file exists. Fee quotes are cached for 5 minutes. The payment flow trusts local UTXO state — if a UTXO turns out to be already spent, ARC will reject with `DOUBLE_SPEND_ATTEMPTED`.

After a successful broadcast, the wallet builds a local transaction model from the data it already has (inputs, outputs, addresses, amounts) and inserts it into the transaction history immediately — no network fetch required. The ARC-returned `txid` is verified against the locally computed `txid` as cryptographic proof that the network accepted exactly what was built.

> **Trust Local State.** Per the Bitcoin white paper (§2), we built the transaction and signed it with our private keys — we know exactly what it contains. There is no need to ask a third party (WhatsOnChain) what we just sent. ARC confirms the network saw it; the rest we already know.

#### Paymail

Paymail allows sending BSV to human-readable addresses (e.g., `user@example.com`) instead of raw Bitcoin addresses. The wallet implements:

- **BRC-30 receive-transaction callbacks** — P2P payment destinations resolved via the `.well-known/bsvalias` capability discovery. The payee's server provides a fresh output script for each payment.
- **Automatic resolution** — when a paymail address is entered in the pay view, the wallet resolves it to a Bitcoin address transparently.

#### Transaction History

- **Direction detection** — incoming (received) vs outgoing (sent), determined by checking whether any inputs belong to the wallet.
- **Grouping** — transactions are grouped by Pending, Today, Yesterday, This Week, This Month, Earlier.
- **Search and filter** — filter by amount, date range, or search by transaction ID.
- **SPV verification** — transactions can be verified against the locally chain-linked block header store anchored to the hardcoded checkpoint.

### UTXO sync

The wallet's UTXO set is reconstructed from locally-held transactions, not queried from a network endpoint. White paper §8 says SPV clients should derive ownership from chain-validated proofs they hold themselves; treating an external `/unspent` index as authoritative inverts that model. Henceforth follows the white paper.

- **History authoritative** — every confirmed transaction in the local store contributes its outputs to the reconstructed UTXO set. WhatsOnChain `/unspent` corroborates and surfaces deposits we haven't fetched yet; it is never the source of truth.
- **Canonical address set** — the wallet's master address, every derived address, and the currently-rotated receive address are unioned into a single set used by both history sync and UTXO reconstruction. A receive address that's been shown to the user can never fall outside this set.
- **Strict removal policy** — a UTXO disappears from the wallet's view only on positive evidence of spend: (1) the user broadcast a transaction that consumes it, (2) a confirmed foreign transaction spending it lands in the local history, or (3) the producing transaction fails SPV verification. Absence from an external endpoint is never a removal trigger.
- **Outpoint-consumption index** — a derived set of "txid:vout" strings recording every consumed output, rebuilt from the local transaction store on every wallet open and updated incrementally as new transactions arrive. The set is append-only and persists pending broadcasts across app death.
- **Reconciliation** — every full sync compares the locally-reconstructed UTXO set against the network's `/unspent` view, partitions outpoints into *corroborated* (both sides agree), *provisional* (we have it, network doesn't yet), and *wallet-unknown* (network has it, we don't). Provisional UTXOs are kept visible; wallet-unknown outpoints trigger a background fetch of the producing transaction so they surface on the next pass.

### Recovery tools

- **Add address** — paste any BSV address into the wallet's edit sheet; the app searches the wallet's seed across both Type42 and BIP-44 chains for a derivation path that produces it. On a hit, the path is attached to the wallet and a targeted sync runs immediately. Pure local computation — no network round-trip during the search.
- **Auto-rediscovery** — when an incoming transaction pays an address the wallet doesn't yet know about, the app silently attempts the same rederivation in the background. A path that exists in the seed is attached automatically before the next sync.
- **Advanced sync toggle** — Settings → Bitcoin → Advanced Sync exposes the active UTXO sync model. Defaults to the legacy network-authoritative path during the rollout window; flip it to enable history-driven reconstruction as the authoritative source. Either side is safe; the toggle exists so users can self-recover if either path surfaces an anomaly.

### SPV Architecture

The wallet implements Simplified Payment Verification per Section 8 of the Bitcoin white paper: clients trust a locally maintained chain of block headers and verify individual transactions against it using Merkle proofs.

> **SPV trust boundary.** Every header in the local store is either the hardcoded checkpoint or transitively chain-links back to it via a series of PoW-validated, chain-linked intermediate headers. There is no silent network fallback in the verification path — if Henceforth doesn't have the header locally, it refuses to verify the transaction and reports a pending-sync state instead.

#### Trust Anchor

The wallet ships with a hardcoded checkpoint in `SPVCheckpoint.mainnet` — a tuple of `(height, hash, previousblockhash, merkleroot, version, time, nonce, bits)` for a recent mainnet block. This is the only header trusted without chain-linkage proof. The current pinned checkpoint is at a block roughly 500 confirmations below the then-tip, providing orders-of-magnitude safety margin against reorganization.

The checkpoint hash doubles as its own migration version marker: bumping `SPVCheckpoint.mainnet` in source automatically triggers a wipe of every user's local header store on next launch, followed by a fresh re-sync from the new anchor.

#### Header Store

The local header store is `FORTH.blockHeaders: [Int: WOCGetHeadersModel]`. Every entry must satisfy four invariants:

1. **Non-empty merkleroot** — enforced by `FORTH.isAuthoritativeBlockHeader`. Pre-Phase-1 placeholder rows are dropped on load.
2. **Individual PoW validates** — double-SHA256 of the serialized header must be below the target encoded in the `bits` field.
3. **Chain-linked to parent** — the header's `previousblockhash` must equal the hash of the header at `height - 1` in the store.
4. **Transitively anchored to the checkpoint** — walking backward through parents eventually reaches `SPVCheckpoint.mainnet`.

#### Validated Tip

`FORTH.validatedTipHeight` is the highest block height whose header transitively chain-links back to the checkpoint via a contiguous run in `blockHeaders`. SPV verification uses `validatedTipHeight` as the trust upper bound, so unvalidated islands are invisible to proof checks.

> **`validatedTipHeight` vs `latestBlockHeight`.** These are different concepts owned by different subsystems. `latestBlockHeight` is the live chain tip (driven by `wocGetHeaders` tip-10 fetch) used for `txVersion` activation gates and UI display. `validatedTipHeight` is "highest height I can prove SPV for right now" (driven by `HeaderSyncService` batch-commit). Never conflate them.

#### Commit Path

`FORTH.commitValidatedHeaderRun(_:)` is the single entry point for adding headers to `blockHeaders` with trust. It requires:

1. The run's first header has a local anchor at `firstHeight - 1`.
2. The anchor's hash equals the run's first `previousblockhash`.
3. The full `[anchor] + run` batch passes `SPVService.validateBlockHeaderChain`, which PoW-validates every header and chain-links consecutive pairs.

#### Auto-Sync Service

`HeaderSyncService` (an `@MainActor` class) runs the background sync loop. On every launch, `ContentView.task` calls `getSavedBlockHeaders` (which enforces the checkpoint seed and recomputes the validated tip) and then `HeaderSyncService.shared.resume(forth:)`.

1. Opens a WebSocket to `wss://socket.whatsonchain.com/websocket/history?from=<validatedTipHeight+1>`.
2. Buffers decoded headers in chunks.
3. When the buffer reaches 500 headers, splits into contiguous runs and flushes each via `commitValidatedHeaderRun`.
4. Idle detection via a cancellable `Task.sleep(for: 3s)` armed on every message — when the sleep completes uncancelled, the WebSocket disconnects cleanly.
5. Exponential backoff from 1s to a 60s cap on retry.

A *force resync* debug button in Settings → Bitcoin → Headers wipes the store back to the checkpoint and restarts sync, behind a confirmation dialog.

#### Bounded Lookup and Verification

`SPVService.verifyTransaction(txid:blockHeaders:checkpointHeight:validatedTipHeight:)` is the single SPV entry point. It:

1. Fetches the TSC (BRC-74) Merkle proof for the transaction from WhatsOnChain.
2. Looks up the containing block header via `findBoundedBlockHeader` — returns the header only when its height falls in `[checkpointHeight ... validatedTipHeight]`.
3. PoW-validates the local header (defense in depth).
4. Verifies the TSC proof against the local header's `merkleroot`.

If step 2 returns nil, verification returns `blockHeaderNotFound` — *without* fetching the header from WoC. A single PoW-valid header in isolation is not SPV: the attacker can produce any chain they like with valid PoW.

#### Checkpoint Maintenance

Bumping the checkpoint is a deliberate operation, not routine:

1. Pick a target block at least 500 confirmations below the current chain tip; never within the last 144 blocks.
2. Fetch the header from a primary source (WhatsOnChain) and **cross-verify** every field against a second independent source.
3. Update `SPVCheckpoint.mainnet` in source. Commit.
4. Every user's next launch detects the new checkpoint hash, wipes the local store, and auto-sync re-downloads from the new anchor.

> **Never bump without cross-verification.** A compromised or cached response at bump time would silently become the new trust anchor baked into the binary shipped to every user. The second source is non-optional.

### Cold Mode and Air-Gap Bundles

Cold Mode is a per-wallet flag (`WalletCard.coldModeEnabled`) that defers broadcast. When set, a transaction the user has approved with Face ID is signed and stored locally as a *pending action* rather than submitted to ARC. The user releases it later from the **Pending Broadcasts** view — on the same device or, in the air-gap workflow, after handing off to a watcher iPhone via AirDrop.

#### Bundle Formats

Three serialisable JSON formats carry data across the air-gap. All three are exchanged via AirDrop, routed by file extension, and validated on import.

- **`.hfheaders` (HFHeaderBundle)** — a contiguous run of validated block headers anchored to a checkpoint hash. The importer hands the run to the same `commitValidatedHeaderRun` path that the live WSS sync uses, so chain-link, proof-of-work, and checkpoint-anchor invariants self-enforce.
- **`.hfreceipt` (HFReceiptBundle)** — proof that a specific transaction was included in the blockchain. Carries (txid, raw transaction hex, block height, block hash, TSC Merkle proof, containing block header). `SPVService.verifyTransaction(fromBundle:)` validates inclusion against the importer's own local header at the same height with no network call. After SPV passes, the importer re-derives output ownership by parsing the raw transaction and refuses unless at least one output's address resolves to one of the wallet's known derived addresses.
- **`.hfaddrpack` (HFAddressPack)** — pre-derived receive addresses pushed outward from signer to watcher. Each entry carries the address, derivation scheme (`type42` or `bip44`), and the scheme-specific derivation reference. The pack is signed by the wallet's m/0/0 BIP32 identity key with a DER ECDSA signature; the watcher's `decode` verifies the signature and refuses tampered packs.

#### Air-Gap Tools UI

**Settings → Bitcoin → Air-Gap Tools** exposes three exporters and a single import button. The importer routes by file extension. Exports go through the system file picker / share sheet so AirDrop, iCloud Drive, and email are all reachable.

> v1 `.hfreceipt` uses raw transaction plus TSC Merkle proof. A v2 schema bump may upgrade to BRC-62 BEEF for full ancestor-script validation.

In v1.0, `.hfaddrpack` import validates the signature and counts the addresses; persisting the entries into a watch-only monitoring store wired to `MempoolMonitorService` is staged for the v1.0.2 follow-up.

### Wallet Data Management

UTXO and transaction persistence is the most security-critical layer of the wallet. The rules below are invariants, not preferences — violating any of them risks losing user funds or transaction history.

- **Never overwrite UTXO files with partial data.** A UTXO file is saved only when *all* addresses queried successfully. A partial query leaves the previous snapshot intact.
- **Conservative merge.** The wallet only removes a UTXO when its owning address was queried *and* the UTXO was not in the response.
- **Never persist a smaller transaction set than what's on disk.** `persistTransactionsToDisk` reads the disk count before writing and refuses the write if the in-memory snapshot has fewer entries.
- **Per-wallet file scoping.** Transactions, UTXOs, and pending broadcast amounts live in wallet-scoped files. On wallet open, in-memory state is cleared and reloaded from that wallet's files only — no cross-wallet bleed.
- **Trust the per-wallet file on load.** Load-time `byOwnership` filtering has been removed because it dropped Type42 change addresses and paymail receives, then silently wrote the smaller set back on the next save.

### UTXOs and Balance

A UTXO (Unspent Transaction Output) represents a discrete amount of Bitcoin that can be spent. The wallet tracks all UTXOs across all addresses.

> **Balance from UTXOs.** The displayed balance is computed solely from the UTXO set — no separate balance API call is needed:
> ```
> confirmed   = sum of UTXOs with block height > 0
> unconfirmed = sum of UTXOs with block height = 0
> total       = confirmed + unconfirmed
> ```
> Satoshi conversions use the named constant `satoshisPerBSV` (100,000,000) and price conversions use `priceCentsDivisor` (100.0). Raw magic numbers are never used.

#### Ordinal Protection

1Sat Ordinals are NFTs inscribed on single-satoshi UTXOs. The wallet protects ordinals at three levels:

1. **Transaction builder** — UTXOs with a value of 1 satoshi are excluded from UTXO selection during transaction building.
2. **Inscription scanner** — for display in the Ordinals view, 1-sat UTXOs are scanned by fetching the raw transaction and detecting the `OP_FALSE OP_IF ... OP_ENDIF` inscription pattern. Results are cached per outpoint.
3. **1Sat indexer fallback** — ordinals transferred to this wallet carry an empty locking script at the receiving output. 1-sat UTXOs with no detectable current-output inscription are checked against the GorillaPool 1Sat indexer. The lookup is tri-state: confirms *is-ordinal*, confirms *not-ordinal*, or fails closed on HTTP 5xx — protecting the UTXO when ambiguous.

#### UTXO Split

From the UTXO detail view, a single UTXO can be split into up to 240 separate outputs across fresh derived addresses. Useful for preparing UTXOs for future transactions, distributing funds across addresses for privacy, and creating multiple 1-sat UTXOs for ordinal inscriptions.

### Security

- **Biometric authentication** — Face ID or Touch ID required to view private keys, seed phrases, and wallet details. Sessions expire after 120 seconds of inactivity. The same window is used by the *payment approval cache* (below).
- **Keychain storage** — all sensitive material (keys, seeds, API tokens) stored with `.whenUnlockedThisDeviceOnly` accessibility — encrypted at rest, tied to the device.
- **Seed verification** — after creating a wallet, users are prompted to verify their seed phrase via a 3-word quiz.
- **No server dependency** — the wallet is fully self-custodial. No account, no registration, no server holds your keys.
- **Message encryption (BRC-2)** — Electrum ECIES format for end-to-end encrypted messages between BSV keys. Uses ECDH key agreement, AES-256-CBC encryption, and HMAC-SHA256 authentication. Wire-compatible with `@bsv/sdk`. Format: `"BIE1" || pubkey || ciphertext || HMAC`.
- **Wallet file encryption** — wallet data files encrypted with AES-256-GCM using a Keychain-backed key before syncing to iCloud.

#### Payment Approval Cache

To avoid re-prompting Face ID for every successive broadcast in a single working session, the wallet keeps a session-scoped *approval cache* (`PaymentApprovalRecord`). A successful biometric approval stamps the cache with `(surface, amountSats, outputsDigest, timestamp)`. A subsequent broadcast within the 120-second window can skip the prompt when all three scoping axes match.

The `outputsDigest` is a SHA-256 over a canonical encoding of the sorted output set. Each output contributes `UInt32-LE(recipientKey.utf8.count) || recipientKey.utf8 || Int64-LE(satoshis)`. The length-prefix defeats engineered concatenation collisions.

> **The `recipientKey` must be the final resolved destination, never an alias.** For paymail surfaces, this means the resolved P2PKH address returned by the paymail server, never the `alice@example.com` alias string. A paymail server could change the resolution between the approval at time T and the broadcast at T+30 seconds — binding the digest to the resolved key forces a re-prompt whenever the destination changes.

#### Encrypted Off-Device Backup

The Keychain-bound wallet encryption above is device-local: the encrypted files on disk are useless on any other device. The *encrypted off-device backup* feature (`.bep` files, produced by `BackupService`) solves this by emitting a portable, password-encrypted blob that can be stored anywhere — iCloud Drive, AirDrop, email, USB — and restored on any device.

- **Key derivation** — PBKDF2-HMAC-SHA256 with a per-backup 16-byte random salt, 600,000 iterations (≈500ms on modern iOS hardware).
- **Encryption** — AES-256-GCM. GCM is authenticated — any bit flip in salt, nonce, ciphertext, or tag fails verification and returns `.invalidPassword` (no timing oracle).
- **Wire format** — magic prefix `"HFBK1"` (5 bytes), salt (16 bytes), iteration count (4 bytes BE), nonce (12 bytes), AES-GCM ciphertext + 16-byte tag.
- **Forward compatibility** — the version byte in the magic prefix allows a future format bump to coexist with older backups.
- **Freshness** — the same plaintext encrypted twice under the same password produces different ciphertexts because salt and nonce are fresh.

> The `.bep` file protects *only the seed phrase* (the BIP-39 mnemonic). It does not contain UTXO cache, transaction history, or user preferences — those are regenerated from the blockchain after restore. A `.bep` plus its password is sufficient to recover every wallet this seed ever spawned on any Henceforth install.

#### QR Code Scanner

A unified QR scanner in Settings handles three QR code types, routed automatically by content:

1. **`hfauth:` prefix** — BRC-103 authentication flow.
2. **WIF private key** (Base58Check version byte `0x80`) — prompts for a wallet name, then imports via `Wallet.restoreFromWIF()`.
3. **Bitcoin address** (version byte `0x00`) — opens the pay view pre-filled with the scanned address.

#### BRC-103 Authentication

BRC-103 provides passwordless authentication to web services using Bitcoin key pairs:

1. A web service displays a QR code containing a challenge and callback URL (prefixed with `hfauth:`).
2. The wallet scans the QR, displays the requesting domain, and asks for user approval.
3. On approval, the wallet signs the challenge with the wallet's identity key and sends the signature to the callback URL.
4. The web service verifies the signature against the wallet's public key.

No passwords, no accounts — just cryptographic proof of key ownership.

#### BRC-100 Wallet Interface

The wallet exposes a subset of its capabilities via a URL scheme for integration with external applications:

```
henceforth://wallet/{method}?params=...
```

Supported operations include key derivation, signing, encryption, and certificate management (BRC-52/53). All sensitive operations require user approval via an on-screen confirmation sheet with biometric authentication.

#### Certificate Proofs (BRC-52/53)

Selective-disclosure certificate proofs follow BRC-52 (field-level HMAC keyring) and BRC-53 (certificate envelope) with the following hardened semantics:

- **Per-field HMAC keyring, ECDH-bound** — when the wallet proves a subset of certificate fields to a verifier, each field's HMAC key is encrypted with an ECDH shared secret derived between the prover's and verifier's BRC-42 identity keys. A leaked proof is useless against any other party.
- **Issuer signature verification** — `verifyProof` checks the issuer's BSM signature over the certificate's canonical field set before accepting any field as authentic. Format-valid is not the same as cryptographically valid.
- **Serial number carried in the proof** — each proof includes the certificate's serial number so the verifier can correlate against revocation or re-issuance records.

### SwiftBSV

The Swift SDK that powers every cryptographic operation in the Henceforth wallet — BIP-32 / BIP-39 key derivation, Type42 (BRC-42) invoice keys, ECDSA signing, BSM, ECIES (BIE1 wire format), Script construction, the full BSV opcode set, transaction building, and SPV verification. Originally written by Will Townsend at [wtsnz/SwiftBSV](https://github.com/wtsnz/SwiftBSV); the fork at [henryhudson/SwiftBSV](https://github.com/henryhudson/SwiftBSV) continues that foundation with Swift 6 strict concurrency, modern Apple platform targets, and a 41-page LaTeX book of its own.

[SwiftBSV Book (PDF)](https://github.com/henryhudson/SwiftBSV/blob/main/Documentation/swiftbsv.pdf)
