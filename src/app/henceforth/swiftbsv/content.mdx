# SwiftBSV

A pure-Swift SDK for Bitcoin SV. SwiftBSV powers the wallet inside Henceforth and ships as a standalone Swift Package for any iOS or macOS app that needs Bitcoin keys, transactions, scripts, or SPV verification.

<a id="goals" />

## Goals

### What SwiftBSV Is

- **Idiomatic Swift.** Value types where they make sense, classes only where mutation lifecycle demands it (`TxBuilder`, `Bip39`). No `NS` prefixes leaking through, no implicit globals, no completion-handler closures where `async`/`await` would do.
- **Compile-time safe.** Optionals where failure is part of the contract (parsing a malformed WIF, decoding a truncated DER signature). Throwing functions where the caller must handle it. No `try!`, no `fatalError` in the production path.
- **Wire-compatible with the rest of BSV.** ECIES emits `BIE1`-format ciphertext readable by `@bsv/sdk`. BSM signatures verify against any other Bitcoin Signed Message implementation. Transaction binary matches whatever a node will accept.
- **Small surface, deep semantics.** Every public type has a single clear responsibility. The *whole* library fits in your head once you've read this book.

### What SwiftBSV Is Not

- Not a wallet. Wallet UX, key storage, address discovery, sync strategy — those live one layer up. SwiftBSV gives you the primitives; Henceforth shows one way to compose them.
- Not a network client. Broadcasting, fee quoting, UTXO fetching, Merkle-proof retrieval — all out of scope. SwiftBSV *validates* a Merkle proof; fetching one over HTTPS is your problem.
- Not a token/ordinal SDK. BSV-20, BSV-21, 1Sat Ordinals, BAP, MAP — all build *on top* of the primitives here. SwiftBSV stays at the protocol layer.

### Future

- Streaming Merkle-tree construction for very large blocks.
- More extensive opcode tests — the Hayes-style suite that covers Henceforth's FORTH side has no exact analogue here yet.
- A formal benchmark suite tracking ECDSA verification and SHA-256 throughput across iPhone generations.

## Cryptographic Primitives

> **Layering.** The types in this chapter are the foundation everything else stands on. You rarely construct them directly — `PrivateKey` hides `BInt`, `PublicKey` hides `Point`, `Hash160` is called for you by `Address`. They're documented here so when you see them in a stack trace or a generic constraint, you know what they mean.

### BInt — Big Integer

Bitcoin keys are 256-bit integers. Swift's `Int` tops out at 64 bits, so SwiftBSV ships its own arbitrary-precision integer type, `BInt`, modeled on the conventional sign-magnitude representation. It conforms to `Comparable`, `Equatable`, `Hashable`, and the standard arithmetic operators.

<Forthbox title="BInt — Constructing 256-bit values">
```swift
let n = BInt("01abcdef", radix: 16)!     // hex literal
let m = BInt(decimalString: "10000000000000000000000")!
let sum = n + m                           // operator overloading
let neg = -m                              // unary minus

if n < m { print("n is smaller") }
```
</Forthbox>

You almost never write `BInt` directly in app code. The library uses it internally for the curve order `N`, the integer form of a private key, and the components of an ECDSA signature.

> `BInt` is `@unchecked Sendable`. The wrapped storage is internally a `Limbs` array of `UInt64`, mutated only inside arithmetic operators that produce new `BInt` values. There is no shared mutable state.

### Point — A Point on secp256k1

`Point` represents an `(x, y)` coordinate on the secp256k1 curve. It is the mathematical content of a public key.

<Forthbox title="Point — Internals you usually don't touch">
```swift
let pubkey: PublicKey = privateKey.publicKey
let point: Point = pubkey.point        // x: BInt, y: BInt

// Compressed serialization (33 bytes)
let compressed: Data = pubkey.toBuffer()

// DER serialization (33 or 65 bytes)
let der: Data = pubkey.toDer(compressed: true)
```
</Forthbox>

You only handle `Point` directly in two places: when you write your own opcode-level script that pushes a curve point, or when you implement a multi-signature scheme by hand. For ordinary signing, encryption, and address derivation, `PublicKey` is the right type.

### Crypto — Hash and HMAC Helpers

The `Crypto` enum bundles the hash functions Bitcoin uses, plus an HMAC helper. Static functions only — no state, no instance.

<Forthbox title="Crypto — Hash functions">
```swift
let bytes: Data = "hello".data(using: .utf8)!

let sha256: Data    = Crypto.sha256(bytes)              // 32 bytes
let sha256d: Data   = Crypto.sha256sha256(bytes)        // 32 bytes (BTC standard)
let hash160: Data   = Crypto.sha256ripemd160(bytes)     // 20 bytes (address hash)
let sha512: Data    = Crypto.sha512(bytes)              // 64 bytes

let key: Data = "secret".data(using: .utf8)!
let mac: Data = Crypto.hmacsha256(key: key, data: bytes)
let mac2: Data = Crypto.hmacsha512(key: key, data: bytes)
```
</Forthbox>

> **Why double SHA-256?** Bitcoin double-hashes nearly everything: transaction IDs, block header hashes, the message-digest step of ECDSA. The doubling defends against length-extension attacks on Merkle–Damgård hash functions and gives a second pass of avalanche even if a structural weakness in the inner hash is later discovered. `Crypto.sha256sha256` encapsulates this so you don't accidentally single-hash where the protocol calls for double-hashing.

#### verifySigData

A combined hash-and-verify helper:

<Forthbox title="Crypto.verifySigData">
```swift
let data: Data = ...                  // arbitrary message bytes
let sig: Data = ...                   // DER-encoded signature
let pub: PublicKey = ...

let ok: Bool = Crypto.verifySigData(
    for: data,
    signature: sig,
    publicKey: pub
)
```
</Forthbox>

The function double-SHA-256s the input before verifying — matching Bitcoin's `checksig` semantics — so you pass the raw payload, not a pre-computed hash.

<a id="keys-and-addresses" />

## Keys and Addresses

### Network

Everything in SwiftBSV that has a wire-format byte representation carries a `Network` enum so the same code can produce mainnet and testnet artifacts:

<Forthbox title="Network">
```swift
public enum Network: Sendable {
    case mainnet
    case testnet
}
```
</Forthbox>

The default everywhere is `.mainnet`. Pass `.testnet` explicitly when you mean it.

### PrivateKey

A `PrivateKey` wraps a 256-bit secret integer (`BInt`), a network tag, and a compression flag.

<Forthbox title="PrivateKey — Constructors">
```swift
// Random key for the given network
let key = PrivateKey(network: .mainnet)

// From 32-byte raw seed
let key2 = PrivateKey(data: bytes, network: .mainnet)

// From WIF (Wallet Import Format) — fails on bad checksum or
// wrong network byte
guard let key3 = PrivateKey(wif: "L1aW4...") else { return }

// Properties
let pub: PublicKey = key.publicKey   // derived on-demand
let addr: Address = key.address      // P2PKH for the network
let raw: Data = key.data             // 32 raw bytes
```
</Forthbox>

#### WIF Round-trip

Wallet Import Format is the standard textual encoding for private keys — a Base58Check string with a network-discriminating version byte:

<Forthbox title="PrivateKey — WIF round-trip">
```swift
let key = PrivateKey(network: .mainnet)
let wif: String = key.toWif()          // "L1aW4...", 52 chars compressed
let restored = PrivateKey(wif: wif)    // returns Optional
```
</Forthbox>

> **Compression flag survives WIF.** A WIF for a compressed key has a trailing `0x01` byte before the checksum is computed. Round-tripping through WIF preserves whether the public key should serialize as 33 bytes or 65 bytes. A "correct" key produces a *different* address depending on its compression bit.

### PublicKey

A `PublicKey` is the curve point a private key derives to, plus its compression flag.

<Forthbox title="PublicKey — Construction & serialization">
```swift
// From hex (33 or 65 bytes)
guard let pk = PublicKey(hex: "02a3b1c...") else { return }

// From DER bytes (33 / 65)
guard let pk2 = PublicKey(fromDer: derBytes, isStrict: true) else {
    return
}

// Serialize back
let derCompressed: Data   = pk.toDer(compressed: true)
let derUncompressed: Data = pk.toDer(compressed: false)
let raw: Data             = pk.toBuffer()  // 33 or 65 bytes

// Address (P2PKH)
let addr: Address = pk.address
```
</Forthbox>

#### Strict vs Lax DER Parsing

The `isStrict` flag on `init(fromDer:isStrict:)` controls whether the parser rejects malformed prefixes. Production callers should always pass `true`; the lax mode exists only for compatibility with historical malleable encodings.

> **Defensive Data slicing.** `init(fromDer:)` explicitly materializes its input via `let buffer = Data(buffer)` before subscripting. A `Data` slice in Swift preserves its parent's indices — subscripting at `[0]` crashes if the slice was taken from a non-zero offset. SwiftBSV defends against this at every `init?` that takes a `Data` parameter.

### Address

`Address` is a P2PKH (Pay-to-Public-Key-Hash) destination. Construction is total — pass any of the upstream key types and you get an address back:

<Forthbox title="Address — Construction">
```swift
let priv = PrivateKey(network: .mainnet)
let addr1 = Address(priv)                      // from PrivateKey
let addr2 = Address(priv.publicKey)            // from PublicKey
let addr3 = Address(bip32, network: .mainnet)  // from a Bip32 node

// Parse a Base58Check string
guard let addr4 = Address(fromString: "1A1zP1...", network: .mainnet)
else { return }
```
</Forthbox>

#### Output Script

To pay an address, you need its locking script:

<Forthbox title="Address — Locking script">
```swift
let script: Script = address.toTxOutputScript()
// OP_DUP OP_HASH160 <20 bytes> OP_EQUALVERIFY OP_CHECKSIG
```
</Forthbox>

`Address` produces a standard P2PKH script. For non-standard outputs (P2SH, multisig, OP_RETURN), build the `Script` directly.

<a id="hd-wallets" />

## HD Wallets — BIP-39 & BIP-32

### Bip39 — Mnemonic Phrases

A 12-word or 24-word phrase from the BIP-39 word list. The phrase encodes 128 or 256 bits of entropy plus a checksum, and deterministically derives a 64-byte seed.

<Forthbox title="Bip39 — Generating a new mnemonic">
```swift
// Standard 24-word phrase (256 bits of entropy)
let phrase: String = Bip39.create(strength: .high)

// 12-word phrase (128 bits of entropy)
let short: String = Bip39.create(strength: .low)

// From specific entropy (e.g. dice-rolled 32 bytes)
let custom: String = Bip39.create(entropy: myEntropy)

// Convert phrase to seed (with optional passphrase)
let seed: Data = Bip39.createSeed(
    mnemonic: phrase,
    withPassphrase: ""
)
```
</Forthbox>

> **The passphrase argument is real.** BIP-39 specifies an optional user passphrase that mixes into PBKDF2 alongside the mnemonic. Two wallets seeded from the same 24-word phrase but different passphrases derive entirely different key trees.

### Bip32 — Hierarchical Deterministic Keys

A `Bip32` node represents a single point in the HD key tree. From the seed produced by `Bip39`, you derive a master node, then descend by path:

<Forthbox title="Bip32 — Master and derivation">
```swift
let seed = Bip39.createSeed(mnemonic: phrase)
let master = Bip32(seed: seed, network: .mainnet)

// Derive m/44'/236'/0'/0/0 (BIP-44 BSV receive address index 0)
guard let node = master.derivedKey(path: "m/44'/236'/0'/0/0")
else { return }

let priv: PrivateKey? = node.privateKey
let pub: PublicKey   = node.publicKey
let addr: Address    = node.address
```
</Forthbox>

#### DerivationNode

Inside the path string, each step is encoded as a `DerivationNode`:

<Forthbox title="Bip32 — DerivationNode">
```swift
public enum DerivationNode {
    case hardened(UInt32)  // 0x80000000 | index
    case notHardened(UInt32)
}

// Equivalent to "m/44'/236'/0'"
let n1 = DerivationNode.hardened(44)
let n2 = DerivationNode.hardened(236)
let n3 = DerivationNode.hardened(0)
```
</Forthbox>

Hardened derivation breaks the public-key-only chain — you cannot derive hardened children from an extended public key alone. This is intentional: it isolates account-level keys from leaf-level exposure.

#### Public-Only Derivation

For watching-only wallets, you can hand someone an extended public key and let them derive child addresses without ever seeing the private side:

<Forthbox title="Bip32 — Public-only mode">
```swift
let masterPub = master.toPublic()
let xpub: String = masterPub.toString()

// On the receiving device:
guard let pubMaster = Bip32(string: xpub) else { return }
guard let leaf = pubMaster.derivedKey(path: "m/0/0")
else { return }
// leaf.privateKey == nil, leaf.publicKey is valid
```
</Forthbox>

> **Path syntax.** `derivedKey(path:)` accepts the conventional `m/<index>['/]` format. Hardened children use `'` (apostrophe). Empty path `m` returns the receiver. Invalid path strings return `nil` — always unwrap.

#### Wire Format

The Base58Check serialization (`xprv...`, `xpub...`) round-trips through `toString()` / `init?(string:)` and matches the BIP-32 specification, byte for byte. SwiftBSV-produced `xprv` can be loaded by any standards-compliant BIP-32 implementation.

<a id="type42" />

## Type42 — Invoice-Numbered Keys

> **Type42 is BRC-42.** The protocol is specified in [BRC-42](https://bsv.brc.dev/key-derivation/0042). SwiftBSV implements the full set: derive private keys, derive public keys, self-derivation, and ECDH shared-secret extraction.

Type42 generates a fresh keypair per invoice number, mixing together one party's private key, the other party's public key, and a string. Two parties who share their public keys offline can independently derive the same address for any invoice number, without ever exchanging private material.

### The Three Derivation Modes

<Forthbox title="Type42 — derivePrivateKey">
```swift
// You have your private key. Counterparty has their public key.
// Both of you can compute the same shared invoice key.
let derived: PrivateKey? = Type42.derivePrivateKey(
    privateKey: myPrivateKey,
    counterpartyPublicKey: theirPublicKey,
    invoiceNumber: "invoice-2026-01-001"
)
```
</Forthbox>

<Forthbox title="Type42 — derivePublicKey">
```swift
// Both parties have only public keys. Useful for watch-only
// wallets that prepare invoices without holding the spending key.
let derivedPub: PublicKey? = Type42.derivePublicKey(
    publicKey: myPublicKey,
    counterpartyPublicKey: theirPublicKey,
    invoiceNumber: "invoice-2026-01-001"
)
```
</Forthbox>

<Forthbox title="Type42 — deriveSelf">
```swift
// Self-derivation — counterparty == self. Used for fresh
// receive addresses inside a single wallet without coordinating
// with anyone.
let receive: PrivateKey? = Type42.deriveSelf(
    privateKey: masterKey,
    invoiceNumber: "wallet/0/recv/42"
)
```
</Forthbox>

### Henceforth Path Conventions

The wallet uses Type42 invoice numbers as a flat namespace:

- `wallet/0/recv/N` — receive addresses (was `m/44'/236'/0'/0/N` in BIP-44)
- `wallet/0/change/N` — change addresses
- `paymail/<handle>` — per-paymail keys
- `bap/<id>` — BAP identity attestation keys

The convenience wrappers `deriveChangeKey`, `derivePaymentKey`, `deriveEncryptionKey`, and `deriveBAPIdentity` build the appropriate invoice-number string and call through to `derivePrivateKey`.

### ECDH Shared Secret

The mathematical operation underpinning Type42 — and ECIES, BRC-103 auth, and any other protocol that needs a shared session key — is ECDH:

<Forthbox title="Type42 — ecdhSharedSecret">
```swift
let secret: [UInt8]? = Type42.ecdhSharedSecret(
    privateKey: myPrivateKey,
    publicKey: theirPublicKey
)
// 33 bytes — compressed serialization of the shared point
```
</Forthbox>

The result is the compressed serialization of the curve point obtained by multiplying the counterparty's public key by your private key. Symmetric: they get the same point by multiplying your public key by their private key.

> **Don't use the raw shared point as a key.** The compressed point has structure — the leading byte is parity, leaving only 256 bits of variable material. For symmetric encryption you should run it through a KDF (BSV uses SHA-512 of the X coordinate to derive an IV, an AES key, and an HMAC key — see the ECIES section).

<a id="signatures" />

## Signatures and ECIES

### Signature — ECDSA Values

A `Signature` bundles `(r, s)`, the sighash type, and a recovery hint. It encodes to two distinct wire formats depending on context:

- **DER** for general ECDSA — variable-length, 70–72 bytes typically.
- **Tx format** for transaction signatures — DER plus a single-byte sighash flag suffix.

<Forthbox title="Signature — Construction & encoding">
```swift
let key = PrivateKey(network: .mainnet)
let messageHash = Crypto.sha256sha256(message)

// Sign produces a Signature value
let sig = ECDSA.sign(
    hash: messageHash,
    privateKey: key
)

// DER bytes — for verification by libsecp256k1, openssl, etc.
let der: Data = sig.toDer()

// Transaction format — DER + sighash byte for OP_CHECKSIG
let txFormat: Data = sig.toTxFormat()

// Verify
let ok = ECDSA.verify(
    hash: messageHash,
    signature: sig,
    publicKey: key.publicKey
)
```
</Forthbox>

> **Sighash byte width.** `toTxFormat` narrows the sighash to the low 8 bits via `UInt8(nHashType.sighash & 0xff)`. Bitcoin's wire format takes a single byte; passing the full 32-bit sighash word would corrupt every transaction.

### Sighash Types

`SighashType` is a bit-or of a base mode and the FORKID flag. BSV defaults to `ALL | FORKID`.

<Forthbox title="SighashType — BSV defaults">
```swift
SighashType.BSV.ALL                    // sign every input + every output
SighashType.BSV.NONE                   // sign every input, no outputs
SighashType.BSV.SINGLE                 // sign every input, only matching output
SighashType.BSV.ALL_ANYONECANPAY       // ALL | ANYONECANPAY
```
</Forthbox>

The FORKID flag was added at the BCH/BSV chain split to prevent transaction replay between BTC and the new chains. Every BSV transaction signature includes it.

### Bitcoin Signed Message (BSM)

BSM is the convention for signing arbitrary text with a Bitcoin private key, returning a Base64-encoded compact signature that any BSM-aware tool can verify against a Bitcoin address.

<Forthbox title="BitcoinSignedMessage">
```swift
let priv = PrivateKey(network: .mainnet)
let addr = priv.address

let msg = "I authorize transaction abc123..."

// Returns Base64 string
let sig: String = BitcoinSignedMessage.sign(
    message: msg,
    privateKey: priv
)

// Anyone with the address + message + signature can verify
let ok: Bool = BitcoinSignedMessage.verify(
    message: msg,
    signature: sig,
    address: addr
)
```
</Forthbox>

The verifier never sees the public key directly: it's recovered from the compact signature and matched against the supplied address.

> **Crash-safety on tampered signatures.** Earlier versions called `try! Secp256k1.recoverCompact(...)` during verification. A signature with an out-of-range recovery flag would crash the host process. The current implementation uses `guard let ... = try? ... else { return false }` — failure to recover means failure to verify, never a crash.

### Recoverable Signatures and Compression

BSM signatures encode a 1-byte recovery header that selects which of up to four candidate public keys was the signer. Two bits encode parity and the second-derivative branch; one extra bit encodes whether the signer's public key was *compressed* when the address was derived. Without the compression bit, `verify` cannot tell whether the recovered key should be hashed in compressed or uncompressed form. SwiftBSV preserves the compression flag across the round trip.

### ECIES (BIE1 Encryption)

> **ECIES, Electrum/BSV flavour.** SwiftBSV implements the *Electrum* variant of ECIES, identified by the wire prefix `"BIE1"`. This is the same format used by `@bsv/sdk`'s `EncryptedMessage` class — ciphertext produced by SwiftBSV decrypts on Node.js, and vice versa.

#### The BIE1 Wire Format

<Forthbox title="BIE1 wire format">
```
"BIE1"  ||  ephemeralPubKey  ||  ciphertext  ||  HMAC
   4              33                  N           32
```
</Forthbox>

The ephemeral public key is 33 bytes (compressed). The HMAC is 32 bytes (HMAC-SHA-256). The ciphertext is AES-256-CBC over the plaintext, padded with PKCS#7. Total overhead is 69 bytes regardless of message length.

#### Key Derivation

The shared secret is the X coordinate of `ephemeralPrivKey * recipientPubKey`. From it:

<Forthbox title="ECIES — key derivation">
```
key = SHA-512(sharedX)
iv  = key[0:16]    // AES-CBC IV
kE  = key[16:32]   // AES-CBC key (128-bit)
kM  = key[32:64]   // HMAC-SHA-256 key
```
</Forthbox>

> **16-byte AES key with a 32-byte HMAC key.** The Electrum format derives a 128-bit AES key (`kE` is 16 bytes) and a 256-bit HMAC key. This matches Electrum's historical choice, not the strongest possible parameter set — but it is the format every BSV implementation has shipped. Don't change the slicing; you'll break interop.

#### API

<Forthbox title="ECIESEncryption — encrypt & decrypt">
```swift
import SwiftBSV

let recipient = PrivateKey(network: .mainnet)
let recipientPub = recipient.publicKey

// Sender does not need their own keypair — ECIES generates an
// ephemeral one per message. Pass nil for senderPrivateKey.
let plaintext: Data = "secret".data(using: .utf8)!
let cipher: Data = try ECIESEncryption.encrypt(
    plaintext: plaintext,
    recipientPublicKey: recipientPub,
    senderPrivateKey: nil
)

// Recipient — only needs their own private key
let recovered: Data = try ECIESEncryption.decrypt(
    ciphertext: cipher,
    privateKey: recipient
)
```
</Forthbox>

#### Authenticated Sender Mode

Pass a sender private key when you want the recipient to know who sent the message. The protocol still uses an ephemeral key for confidentiality, but the HMAC is keyed in a way the recipient can validate against the named sender.

<Forthbox title="ECIES — Authenticated sender mode">
```swift
let sender = PrivateKey(network: .mainnet)
let cipher = try ECIESEncryption.encrypt(
    plaintext: data,
    recipientPublicKey: recipientPub,
    senderPrivateKey: sender
)

// Recipient supplies their own private key + the expected
// sender public key. HMAC failure means either the message
// was tampered or the sender wasn't who you expected.
let recovered = try ECIESEncryption.decrypt(
    ciphertext: cipher,
    privateKey: recipient,
    senderPublicKey: sender.publicKey
)
```
</Forthbox>

#### Errors

`ECIESError` is a small enum:

- `.invalidPublicKey` — the embedded sender public key didn't deserialize as a valid curve point
- `.hmacMismatch` — ciphertext failed authentication
- `.invalidCiphertextFormat` — wrong magic prefix, truncated input, or non-canonical encoding
- `.encryptionFailed` / `.decryptionFailed` — AES-CBC failure (typically padding)

<a id="scripts" />

## Scripts and Opcodes

### Script Anatomy

A Bitcoin `Script` is a sequence of `Chunk`s — each chunk is either a single opcode or a `PUSHDATA` containing literal bytes.

<Forthbox title="Script — Standard P2PKH">
```swift
let priv = PrivateKey(network: .mainnet)
let addr = priv.address

// Build by hand
var script = Script()
_ = script
    .append(.OP_DUP)
    .append(.OP_HASH160)
    .appendData(Crypto.sha256ripemd160(priv.publicKey.toBuffer()))
    .append(.OP_EQUALVERIFY)
    .append(.OP_CHECKSIG)

// Or use the convenience
let sameScript = addr.toTxOutputScript()
```
</Forthbox>

### Opcode Catalogue

Opcodes live in `Sources/SwiftBSV/Scripts/OP_CODE/` grouped by category:

- **Push Data** — `OP_FALSE/0`, `OP_PUSHDATA1/2/4`, `OP_1NEGATE`, `OP_1`…`OP_16`
- **Flow Control** — `OP_NOP`, `OP_IF`, `OP_NOTIF`, `OP_ELSE`, `OP_ENDIF`, `OP_VERIFY`, `OP_RETURN`
- **Stack** — `OP_DUP`, `OP_DROP`, `OP_SWAP`, `OP_OVER`, `OP_ROT`, `OP_PICK`, `OP_ROLL`, `OP_DEPTH`…
- **Splice** — `OP_CAT`, `OP_SPLIT`, `OP_NUM2BIN`, `OP_BIN2NUM`, `OP_SIZE`
- **Bitwise Logic** — `OP_INVERT`, `OP_AND`, `OP_OR`, `OP_XOR`, `OP_EQUAL`, `OP_EQUALVERIFY`
- **Arithmetic** — `OP_ADD`, `OP_SUB`, `OP_MUL`, `OP_DIV`, `OP_MOD`, `OP_BOOLAND`, `OP_BOOLOR`…
- **Crypto** — `OP_HASH160`, `OP_HASH256`, `OP_SHA1`, `OP_SHA256`, `OP_RIPEMD160`, `OP_CHECKSIG`, `OP_CHECKMULTISIG`
- **Lock Time** — `OP_CHECKLOCKTIMEVERIFY`, `OP_CHECKSEQUENCEVERIFY`
- **Reserved Words** — the Chronicle-restored opcodes that BSV brought back from the original protocol set

The full enumeration is exhaustive — BSV restored every opcode that BTC removed at the chain split. The library exposes them all as enum cases on `OpCode`.

> **Script vs FORTH.** Henceforth's FORTH terminal is the human-facing interface to script construction — you type `OP_DUP OP_HASH160 ... OP_CHECKSIG` and the recorder emits the bytes. SwiftBSV's `Script` type is the programmatic interface, used by `TxBuilder` and by anyone embedding script construction inside a Swift host.

## Transactions and TxBuilder

### Transaction Structure

A BSV transaction is the same algebraic object the white paper describes:

<Forthbox title="Transaction — Structure">
```
Transaction
  +-- version            (4 bytes)
  +-- inputs             (varint count + N inputs)
  |     \-- (prevTxid, prevVout, scriptSig, sequence)
  +-- outputs            (varint count + M outputs)
  |     \-- (value, scriptPubKey)
  \-- lockTime           (4 bytes)
```
</Forthbox>

SwiftBSV exposes `Transaction`, `TransactionInput`, and `TransactionOutput` as value types. You can construct one by hand, but the `TxBuilder` fluent API is the conventional path.

### TxBuilder — Fluent Construction

`TxBuilder` is a class (not a struct) because building a transaction is a sequence of mutations against an evolving state, and a class lets you chain calls that all return `self`.

<Forthbox title="TxBuilder — A complete pay-to-address transaction">
```swift
let alice = PrivateKey(network: .mainnet)
let bob   = Address(fromString: "1A1zP1...", network: .mainnet)!

let utxo: TransactionOutput = ...   // from your UTXO source
let prevTxid: Data           = ...
let prevVout: UInt32         = 0

let builder = TxBuilder()

_ = builder
    .setVersion(2)
    .setFeePerKb(50)
    .setChangeAddress(alice.address)
    .inputFromPubKeyHash(
        txHashBuffer: prevTxid,
        txOutNum: prevVout,
        txOut: utxo,
        pubKey: alice.publicKey
    )
    .outputToAddress(value: 50_000, address: bob)

let built = try builder.build(useAllInputs: true)

// Sign every input
for i in 0..<built.transaction.inputs.count {
    _ = built.signInTx(
        nIn: i,
        privateKey: alice
    )
}

let raw: Data = built.transaction.serialized()
let txid: String = built.transaction.txID
```
</Forthbox>

#### Method Reference

<Forthbox title="TxBuilder — Setters & inputs">
```swift

.setNLockTime(_ nLockTime: UInt32)
.setFeePerKb(_ fee: Float)
.setChangeAddress(_ changeAddress: Address)
.setChangeScript(_ changeScript: Script)

    txHashBuffer: Data,

)

.outputToScript(value: UInt64, script: Script)
```
</Forthbox>

#### build(useAllInputs:)

`build(useAllInputs:)` computes a final fee against `feePerKb`, picks UTXOs to cover the outputs, and emits a change output if there's leftover value. Pass `true` to force every added input into the final transaction; pass `false` to let the builder pick the minimum subset.

#### signInTx(nIn:privateKey:)

Signs a single input with the supplied private key. Repeat for every input. The signature uses `SighashType.BSV.ALL | FORKID` by default.

> **Build, then sign — always in that order.** `build` computes input/output structure and locks down the transaction shape. Signing earlier produces signatures over a transaction that no longer exists by the time `build` mutates the input set.

### Parsing a Transaction

`Transaction.deserialize(_:)` is the inverse of `serialized()` — it reconstructs the value type from wire bytes. Those bytes are almost never yours: they arrive from a peer, a block, a pasted hex string, a QR code, a dApp handing you a transaction to inspect. So `deserialize` is a *throwing* function, and failure is part of its contract.

<Forthbox title="Transaction — Parsing wire bytes">
```swift
let raw: Data = ...   // from the network, a file, a paste — untrusted

do {
    let tx = try Transaction.deserialize(raw)
    // tx.inputs, tx.outputs, tx.txID — safe to read
} catch {
    // DeserializationError — truncated or structurally invalid; reject it
}
```
</Forthbox>

Every read inside the parser is bounds-checked before it runs. A buffer that ends in the middle of a script, an input count that claims more inputs than the remaining bytes can hold, a length prefix that overflows `Int` — each throws `DeserializationError` rather than reading past the end:

- `.unexpectedEndOfStream` — a read ran off the end of the buffer. The input is truncated.
- `.malformedData` — a length or count field declares a value too large to represent. The input is structurally invalid, not merely short.

> **A bounds check written in trapping arithmetic is not a bounds check.** The obvious guard — `guard offset + Int(length) <= data.count` — isn't defensive: when `length` is an attacker-controlled varint above `Int.max`, the `Int(_:)` conversion *traps while evaluating the guard's own condition*, before the comparison ever runs. The crash happens inside the check meant to prevent it. SwiftBSV converts with `Int(exactly:)` and adds with `addingReportingOverflow` — both report failure instead of trapping — so the check itself can never crash. The BEEF envelope parser (`BEEFParser.parse`, BRC-62) is held to the same contract.

## Simplified Payment Verification

> **What SwiftBSV does in SPV.** The library implements the *verification* side: given a block header, validate its proof-of-work; given a chain of headers, validate that each links to its parent; given a Merkle proof, validate that a transaction belongs to a header's Merkle root. The library does *not* fetch headers or proofs — that's the consumer's job.

### BlockHeader Protocol

Anything that can answer the eight standard fields conforms to the `BlockHeader` protocol. You don't have to use SwiftBSV's own model type — WhatsOnChain's `WOCGetHeadersModel` (in Henceforth) conforms directly:

<Forthbox title="BlockHeader protocol">
```swift
public protocol BlockHeader {
    var hash: String { get }
    var height: Int { get }
    var version: Int { get }
    var merkleroot: String { get }
    var time: Date { get }
    var nonce: Int { get }
    var bits: String { get }
    var previousblockhash: String { get }
}
```
</Forthbox>

### BlockHeaderValidator

The validator runs three checks:

<Forthbox title="BlockHeaderValidator">
```swift
let validator = BlockHeaderValidator()

// 1. Single-header proof-of-work
let powOK: Bool = validator.validateProofOfWork(header: header)

// 2. Chain-link to parent
let linkOK: Bool = validator.validateChainLink(
    header: child,
    previousHeader: parent
)

// 3. Full chain — sorts by height, validates PoW + linking
let result: ChainValidationResult =
    validator.validateHeaderChain(headers: headers)

if result.isValid {
    print("validated \(result.validatedCount) headers")
} else {
    print(result.errorMessage ?? "unknown error")
}
```
</Forthbox>

#### Block Hashing

<Forthbox title="BlockHeaderValidator.calculateBlockHash">
```swift
// Serialize the 80-byte header
let serialized: Data? = validator.serializeBlockHeader(header: h)

// Double-SHA-256 and reverse to display byte order

```
</Forthbox>

#### Target from Bits

The `bits` field encodes the difficulty target in compact form:

<Forthbox title="Target arithmetic">
```swift
let target: UInt256? = validator.targetFromBits(bits: header.bits)

// PoW passes if computed hash, interpreted as UInt256,
// is strictly less than target
let hashValue: UInt256? = UInt256(hexString: computedHash)
let powOK = hashValue! < target!
```
</Forthbox>

`UInt256` is a custom big-endian 256-bit comparable struct.

### Merkle Proof Formats

SwiftBSV understands three Merkle proof formats:

- **Standard `MerkleProof`** — generic representation: `(txid, blockHash, index, nodes)`.
- **TSC (BRC-74) `TSCMerkleProof`** — the Technical Standards Committee compact format used by BSV miners and indexers.
- **WhatsOnChain `WOCMerkleProof`** — the WoC API response shape with directional branches (`"L"` / `"R"`).

<Forthbox title="MerkleVerifier — Standard proof">
```swift
let proof = MerkleProof(
    txid: "...",
    blockHash: "...",
    blockHeight: 800_000,
    merkleRoot: "...",
    index: 42,
    nodes: ["aaaa...", "bbbb...", ...]
)

let verifier = MerkleVerifier()
let ok = verifier.verifyMerkleProof(
    proof,
    expectedMerkleRoot: header.merkleroot
)
```
</Forthbox>

<Forthbox title="MerkleVerifier — TSC (BRC-74)">

```swift
    txOrId: "...",

    proofType: "branch",
    composite: false
```

</Forthbox>

#### Pair Hashing in Display vs Wire Order

The trickiest part of Merkle verification is the byte-order convention. Bitcoin hashes appear in the API and the UI in *display* order (most significant byte first), but the underlying double-SHA-256 operates on *wire* order (least significant byte first). `doubleSHA256HashPair` encapsulates this:

<Forthbox title="doubleSHA256HashPair">
```swift
public func doubleSHA256HashPair(left: String, right: String) -> String {
    let leftBytes = Data(hex: left)
    let rightBytes = Data(hex: right)

    var combined = Data(leftBytes.reversed())
    combined.append(Data(rightBytes.reversed()))

    let hash1 = Data(combined).sha256()
    let hash2 = Data(hash1).sha256()

    return Data(Data(hash2).reversed()).hex
}
```
</Forthbox>

The two reversals — on input and on output — mean the function takes display-hex in and produces display-hex out, while internally hashing in wire order.

> **Defense in depth.** Even when verifying a Merkle proof against a header's `merkleroot`, you should validate the header's PoW *before* accepting the proof. A header with a wrong `merkleroot` could be served to you by a hostile API; an attacker who controls one endpoint cannot also produce a valid PoW pre-image. Always sequence: (1) PoW-validate the header, (2) verify the Merkle proof against the validated header's root, (3) only then declare the transaction confirmed.

### SPV Errors

`SPVError` is the closed enum returned by verification failures:

- `.invalidMerkleProof` — the proof structure is malformed
- `.blockHeaderNotFound` — the consumer was asked to verify against a header it doesn't have
- `.merkleRootMismatch` — the proof verified to a different root than the header
- `.invalidProofFormat` — format-level rejection
- `.networkError(String)` — carried up from the consumer's network layer
- `.txNotInBlock` — proof unavailable for the transaction (typical when a tx is mempool-only)
- `.invalidBlockHash` — the block hash failed PoW or didn't link
- `.headerChainNotSynced(requiredHeight: Int, localTip: Int)` — the tx is in a block above the locally validated tip; the consumer should retry once sync catches up, not present this as a verification failure

The distinction between `.blockHeaderNotFound` and `.headerChainNotSynced` is what lets the consumer show *"⏳ SPV PENDING"* for sync gaps and *"✗ SPV FAILED"* for genuine verification failures.

#### Swift 6 Concurrency Notes

Every public type that crosses an actor boundary in real code is `Sendable`. You can pass `PrivateKey`, `PublicKey`, `Address`, `Bip32`, `Signature`, `MerkleProof`, and `ChainValidationResult` freely between `@MainActor` and detached `Task` contexts.

A small number of types remain non-`Sendable` because mutation is part of their interface:

- `TxBuilder` — holds an evolving `Transaction`; mutate it on one isolation domain and pass the resulting `Transaction` (which *is* `Sendable`) across boundaries.
- `Bip39` — a static-only entry point in practice; the class itself is not constructible.

> **No `@preconcurrency import SwiftBSV` required.** Earlier Henceforth code carried `@preconcurrency import` on five files because not every type was `Sendable`. The current build is clean. If you find yourself needing `@preconcurrency` against SwiftBSV, file an issue: it's a bug in the library, not your consumer.
