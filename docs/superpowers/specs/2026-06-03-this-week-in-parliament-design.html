This Week in Parliament phase 1

2026-06-03 · design spec · A weekly, recess-aware digest of what the House of Commons voted on and was asked, published to henceforth.club/hansard/this-week and Twitter every Wednesday before noon PMQs. Phase 1 of a civic-pressure flywheel; this round is the audience-building digest only — the MP-pressure mechanism is the documented north star, not built here.

One-line summary: a Vercel Cron pulls the week's Commons divisions and written questions from the official Parliament APIs, computes headline stats and a questions-by-department chart, ranks a handful of highlights and has an LLM write short blurbs in a cheeky-but-credible voice — then lands it as a draft the owner reviews and approves before it publishes to a Next.js page and is posted (manually) to Twitter. It runs every week, switching to a "they're on their holidays" treatment during recess (verified against Parliament's published recess calendar, never guessed).

Why this is marketing content, not an app feature. This lives entirely in the henceforth-club Next.js site — not the Hansard iOS app. Its job is top-of-funnel: build an audience (Twitter following + SEO-able web archive) and drive 99p app downloads. No Swift is touched. The eventual pay-off — turning that audience's demand into organised pressure on MPs — is Phase 2/3.

1 · Goals & non-goals

Goal. Ship a repeatable weekly pipeline that, every Wednesday morning, turns the previous parliamentary week into a published, shareable digest — a web page at /hansard/this-week and a Twitter-ready chart image + thread — with the owner approving each issue before it goes live. The digest must be accurate (numbers and the chart come straight from official API data), skimmable, on-brand (cheeky-but-credible), and never publish an empty or misleading page (recess-aware, human-gated).

Non-goals (this phase). No email, newsletter platform, subscribe form, or owned list. No constituency capture (it returns with the pressure mechanism). No semantic topic classification — department breakdown only. No auto-posting to Twitter (owner posts manually). No changes to the Hansard iOS app or any Swift. No personalisation / per-MP digests. No comments, accounts, or user data of any kind.

2 · Architecture — one source of truth

A pure data flow with the official Parliament APIs as the single authority. Effects (HTTP fetches, the LLM call, writing the draft, deploying) sit at the edges; the middle — stats, the department histogram, highlight ranking, mode selection, window maths — is total functions over plain data, so the numbers cannot disagree with what Parliament actually did, and every transform is unit-testable.

  Wednesday 05:00 UTC — Vercel Cron
        │   window = (last Wednesday 00:00 .. this Wednesday 05:00), London-aware
        ▼
  Fetch (effects, at the edge):
    • Commons Votes API        → divisions in window
    • Written Questions API    → questions in window (+ answeringBodyName, asker)
    • Bills API                → bills with stage movement in window
    • Recess calendar          → is the House sitting this window?
        ▼
  Compute (pure, tested):
    DigestData {
      window, mode: normal | quiet | recess,
      stats: { mps, questions, divisions, distinctAskers },
      departmentHistogram: [ { body, count } ],     ← the chart
      highlights: { votes[], questions[], bills[] }  ← ranked, top-N
    }
        ▼
  Narrate (effect — one bounded LLM call):
    short blurbs per highlight + a mode-appropriate intro, cheeky house voice
        ▼
  Draft  →  owner reviews  →  APPROVE  →  publish (ISR page) + chart image
                                          → owner posts to Twitter (manual)

Why diff-and-count instead of editorial logic: the chart is just a histogram of answeringBodyName; the headline numbers are counts over the window; "mode" is a function of (activity level, recess-calendar). None of it needs to understand politics, so none of it can get the politics wrong — the only judgement calls (which highlights, how to phrase them) are quarantined into the ranking heuristic and the single LLM step, both downstream of verified numbers.

3.2 · The weekly generator (the Cron pipeline)

A Vercel Cron-triggered serverless function (the /api surface already exists in the repo). On each run it executes the §2 flow and writes a draft — it does not publish. Data fetches are re-implemented in TypeScript against the public REST APIs (the Swift clients in the iOS app are reference only). The LLM step uses Anthropic (same provider as the existing daily-review automation), one bounded call per issue.

3.3 · The three modes & recess detection

ModeTriggerTreatment
normalHouse sat; meaningful activity in window.Full digest — stats, chart, ranked highlights.
quietHouse sat (per calendar) but little happened.Lighter digest, "slow week in the Commons." Not "on holiday" — they were there.
recessRecess calendar confirms the House did not sit.Cheeky "Parliament's on its holidays 🏖️" — 0 votes / 0 new questions, a countdown to their return date, optional one throwback stat or "what's coming when they're back."

Recess is verified, not inferred from emptiness. A genuinely quiet sitting week and a recess week both look near-empty in the data — but only one is "they're on holiday." Cross-referencing Parliament's published recess dates is what separates a credible joke from a factual error. The recess calendar source (an API endpoint or a maintained constant of the published dates) is resolved at build; it also supplies the accurate "back on [date]" line.

3.4 · Draft → approve → publish (the "C" loop)

The human-in-the-loop is the whole point of mode C. Two implementation options, decided at planning time:

OptionHow approval worksTrade-off
(a) git-PRThe Cron commits the draft DigestData (JSON/MDX) to a branch and opens a PR. The owner's PR review IS the approval. Merge → Vercel deploys → page live.No database; fully versioned; native to how the owner already works. Needs a GitHub token in the Cron and a PR-automation step.
(b) KV + adminDraft stored in Vercel KV; a protected preview route shows it with an "Approve & Publish" button that flips status: draft→published.Self-contained; needs an auth-gated admin route and a small KV store.

Recommendation: start with (a) git-PR — zero new infrastructure, the digest history lives in git, and reviewing a PR is already the owner's daily-review muscle. Fall back to (b) only if Cron→GitHub automation proves fiddly.

4 · Scheduling & the parliamentary week

Cron expression 0 5 * * 3 — 05:00 UTC every Wednesday. Because Vercel Cron is UTC and the UK observes DST, this lands ~05:00 London in winter (GMT) and ~06:00 in summer (BST) — both comfortably before a 07:00 post and far before noon PMQs, with no per-season cron juggling. Precise weekly scheduling requires Vercel Pro (Hobby crons are best-effort daily); the site is already on a paid plan for the daily reviews.

The window is last Wednesday 00:00 London → this Wednesday 05:00 London. Window maths must be DST-correct (compute in Europe/London, not naive UTC arithmetic) — a unit-tested pure function. If the owner finds a same-morning review too tight to rely on weekly, the alternative is generating Tuesday evening and reviewing at leisure; the pipeline is identical, only the cron expression changes.

6 · House voice

Informative with a cheeky edge — credible enough that the numbers are trusted, with enough personality to be shareable. Encoded as a reusable system prompt for the LLM step, with the mode passed in (a recess intro is openly playful; a normal-week intro is wry but straight). The voice never editorialises the numbers — only the framing.

7 · Distribution

Website is canonical and permanent (archive + SEO). Twitter is the reach channel: the generator produces a chart image; the owner posts it natively with the 2-3 sharpest items and a link to the page (native value first — X throttles link posts, so the thread must stand alone). Auto-posting is explicitly out of scope this phase.

8 · Error handling

  • Fetch or LLM failure → the draft simply doesn't complete. Because publishing is human-gated, a failed/partial run can never ship a broken page or post. Retry next week or re-run manually.
  • Idempotency → the generator is keyed by week; re-running the same Wednesday overwrites that week's draft, never duplicates.
  • Partial data → if one source is down (e.g. Bills API), the digest renders the sections it has and notes the gap, rather than failing whole.
  • Recess-calendar miss → if recess status can't be determined, fall back to quiet mode (never assert "on holiday" without confirmation).

9 · Testing

The pure core is the test surface (vitest):

  • Window maths — last-Wed→this-Wed in Europe/London, including the two DST changeover weeks.
  • Stats & department histogram — counts and grouping over fixture API payloads.
  • Mode selection — normal / quiet / recess given (activity, recess-calendar) combinations, incl. the "quiet sitting week must not say holiday" case.
  • Highlight ranking — deterministic top-N over fixtures.
  • Page render — renders from a DigestData fixture for each mode (component/snapshot).

The LLM step and live fetches are mocked in tests; a thin live-smoke check (real APIs, no publish) can be run manually before the first real issue.

10 · North star — deferred phase 2 / 3

The reason the audience matters: apply organised pressure on MPs to ask the questions users want. The highest-leverage unit is a verified constituent contacting their own MP, and legitimacy (real constituents, not bots) is the whole asset. Phase 1 deliberately does not capture constituency (no email/form this round), so Phase 2 owns the demand-capture (a constituency-aware "what do you want asked?" surface) and Phase 3 the pressure mechanism (constituent→own-MP action, a public demand tally, escalation to official petitions — petition.parliament.uk is already integrated in the app). Phase 1's only obligation to the north star is to not foreclose it — and a separate web capture surface slots in cleanly later.

11 · Decided at planning time

  • Approval mechanism: git-PR (recommended) vs KV+admin.
  • Recess-calendar source: Parliament endpoint vs maintained constant.
  • Exact API endpoints / params / field names (verified live).
  • Chart rendering lib for the page (e.g. lightweight SVG / Recharts) and the share-image generator.
  • Generation cadence if same-morning review is too tight (Wed 05:00 vs Tue evening).
