/whh — the weekly review

Design · 2026-06-29 · a higher-altitude aggregator over the daily /hh review: how the week went, how to do better, and what App Store Connect says about driving sales · credentials prerequisite before the sales half runs

One-line: a hand-run /whh ("Weekly HH") command that reads the week's already-persisted daily-review artifacts and the kanban, computes the numbers deterministically, has an ultracode agent layer write the judgement (what went well, what to change next week), pulls real paid-units / proceeds / funnel data from App Store Connect, and publishes the whole thing to a gated /board/week page on henceforth.club so it is readable full-screen from any device.

Provenance: every path, schema, and constraint below was verified on 2026-06-29 by a three-agent read-only investigation of (a) the live /hh command and its persisted artifacts, (b) the henceforth-club board plumbing, and (c) App Store Connect access on this machine. The non-obvious findings — chiefly that no analytics data or fetch-tooling exists locally yet — are flagged inline. Open prerequisites are collected at the end.

Goal & scope

The daily /hh re-adjudicates the automated review emails and updates the Morning Board each morning. It leaves durable, dated traces but never looks across days. /whh is the weekly lens: it answers two questions you asked — "how did we do and how can we do better next week" (retrospective, from data that already exists) and "what does the analytics say, to drive more sales" (growth, from a new App Store Connect data path). These two halves have very different cost profiles and are designed to fail independently — the retrospective runs with zero new credentials; the sales half is gated on them.

The report series is the spine, not the kanban. The board dates findings only informally (inside id/source/desc strings), so it is a weak time-series. Analysis engine — hybrid (deterministic numbers, agent judgement)

This is the load-bearing design choice, taken over the two extremes.

Why not pure-agent, why not pure-script. A pure-agent analysis is articulate but non-reproducible — the same week would yield drifting counts run to run, and you could not trust "confirmed defects fell 40%." A pure deterministic script is trustworthy but mute — it cannot notice that you spent three mornings re-litigating the same already-rejected finding. So the work splits on a trust boundary: a deterministic aggregator owns every number (weekly totals, throughput, week-over-week deltas, recurring-reflag counts), and an ultracode Workflow synthesis layer owns every judgement (wins, misses, next-week actions, which sales lever to pull). This mirrors how /hh itself already separates deterministic local CI gates from agent adjudication — same boundary, one altitude up.

Metrics — the retrospective half

Computed deterministically, then handed to synthesis as ground truth.

  • Weekly totals + per-app: sum of each daily summary field across the covered days — reviews, confirmed, rejected, abstained, alreadyResolved, boardMoves, newConfirmedDefects, verdictsSurvivedRefutation — overall and split by app (deck, henceforth, hansard, provenance).
  • Throughput: cards that reached done this week vs. cards that entered review/inprogress; net open delta; and stuck items — cards sitting in inprogress/review beyond a threshold (estimated from id/source dates + the log).
  • Recurring re-flags: findings that appear across multiple days' corrections ledgers or repeated rejections — e.g. the known CertificateStore / nil-billId carry-forwards. Each gets a count, first-seen date, and current status. This is the highest-leverage "do better" signal: it quantifies wasted re-adjudication.
  • Signal ratios: confirm-vs-reject ratio, abstain rate, and how many verdicts survived adversarial refutation — a read on review quality, not just volume.

Metrics — the sales half

The constraint that shapes this whole half: there is currently zero analytics data on this machine and no tooling to fetch it. Both apps are paid-up-front — no in-app purchases, no subscriptions, no telemetry SDK — so the only money-metric is paid units × price, which lives exclusively in App Store Connect. "Drive more sales" therefore cannot be answered from local data; it needs a new App Store Connect API path. That path is cheap to build (the .p8 keys already exist) but needs three small inputs from you (end of doc).

Two App Store Connect surfaces, in two tiers:

TierSurfaceYieldsAvailability
1 — the numberSales and Trends Reports (GET /v1/salesReports, frequency=WEEKLY)Paid units + proceeds per app, per market. The real "sales" figure for paid apps.Synchronous; previous day onward; needs the vendor number.
2 — the funnelApp Analytics Reports (POST /v1/analyticsReportRequests → poll → segment URLs)Impressions → product-page views → downloads → conversion rate. The "why sales are what they are" signal.Asynchronous; a one-time ONGOING report request per app, then ~1–2 days before Apple backfills.

Sales-driver suggestions hang off the weakest funnel stage: low impressions → search-keyword / App Store optimisation work; healthy impressions but low product-page views → icon / screenshots / subtitle; healthy views but low conversion → description, screenshots ordering, price, ratings prompts. Tier 1 ships in v1 immediately (units + proceeds + week-over-week); Tier 2 lights up once the report request has been live a couple of days, and the synthesis degrades gracefully — qualitative suggestions when the funnel numbers are not yet present.

App Store Connect integration — the new data path

A small Node client living beside the existing scripts/board/*.mjs tooling (keeping everything in one runtime). It mints a short-lived ES256 JWT from your existing ~/.appstoreconnect/*.p8 key and calls the two surfaces above.

JWT (per call, ≤20 min expiry — Apple rejects longer):
  header  { alg:"ES256", kid:<Key ID>, typ:"JWT" }
  payload { iss:<Issuer ID>, iat, exp, aud:"appstoreconnect-v1" }
  signed with ~/.appstoreconnect/AuthKey_<KeyID>.p8   (never copied, never committed)

Sales (Tier 1):
  GET /v1/salesReports?filter[frequency]=WEEKLY
       &filter[reportType]=SALES&filter[reportSubType]=SUMMARY
       &filter[vendorNumber]=<vendor>&filter[reportDate]=<YYYY-MM-DD>&filter[version]=1_1
  → gzipped TSV; parse Units + "Developer Proceeds" per app SKU.

Analytics (Tier 2, one-time setup then poll):
  POST /v1/analyticsReportRequests   { accessType: ONGOING, app: <appId> }
  → poll analyticsReportRequests/{id}/reports → reports/{id}/instances
  → reportInstances/{id}/segments → gzipped CSV download URLs.

Three App Store Connect gotchas the client must handle: (1) Sales reports come back as gzipped TSV, not JSON — decompress and parse columns, don't expect a JSON body. (2) The Sales endpoint needs a vendor number (the 8-digit id from Payments and Financial Reports) in addition to the Issuer ID — a different identifier. (3) Apple's sales calendar lags ~1 day and uses fiscal weeks; the client requests the most recent available reportDate and labels the window honestly rather than assuming "today minus 7."

Credentials stay local — only aggregates are published. The Issuer ID, Key ID, vendor number, and .p8 path go in henceforth-club/.env.local (where the Upstash secrets already live, gitignored); the .p8 itself stays at ~/.appstoreconnect/. Nothing secret is ever written to content/, committed to git, or pushed to Upstash — only the computed units / proceeds / funnel numbers reach the website. This matches the release pipeline's "base64 the key, pass via env, never to disk" stance and your standing keep-keys-local rule.

Durable artifact — weeks/<date>.json

The weekly analogue of the daily reports/<date>.json, so a future monthly/quarterly view can aggregate weeks the same way /whh aggregates days.

{
  weekOf, weekEnd, generatedAt,
  daysCovered: ["2026-06-23", …],            // reports that actually existed
  retro: {
    totals: { reviews, confirmed, rejected, abstained, alreadyResolved,
              boardMoves, newConfirmedDefects, verdictsSurvivedRefutation },
    perApp: [ { app, name, reviews, confirmed, rejected, abstained, shipped } ],
    throughput: { movedToDone, enteredReview, netOpen,
                  stuck: [ { id, title, app, col, daysInColumn } ] },
    recurringReflags: [ { signature, app, timesFlagged, firstSeen, status, note } ],
    ratios: { confirmRejectRatio, abstainRate, survivedRefutation },
    wins: [string], misses: [string],
    nextWeek: [ { tag, title, detail } ]       // agent-written, mirrors plan.items shape
  },
  sales: {
    window: { thisWeek, lastWeek },
    perApp: [ { app, name,
      units:    { thisWeek, lastWeek, deltaPct },
      proceeds: { thisWeek, lastWeek, currency, deltaPct },
      funnel?:  { impressions, productPageViews, conversionRate } } ],   // Tier 2, optional
    drivers: [ { app, lever, rationale, action } ]
  }
}

The nextWeek items reuse the daily plan.items shape ({ tag, title, detail }) so they could later be promoted into board cards by /hh with no reshaping.

The /whh command

A global slash command at ~/.claude/commands/whh.md, a sibling to ~/.claude/commands/hh.md, run by hand. Default window: the trailing 7 days ending today. Its orchestration:

  1. Resolve the window and the set of reports/<date>.json that exist within it.
  2. Run the deterministic aggregator (numbers) + the App Store Connect pull (sales).
  3. Run a Workflow: parallel readers (retro · throughput · reflags · sales) → synthesis agent → the weeks/<date>.json object.
  4. Write the artifact, run publish-week.mjs, print a chat summary with the /board/week link.

What v1 deliberately won't do yagni

  • No launchd automation — you run /whh, as chosen. The "This Week in Parliament" weekly agent stays the only scheduled weekly job.
  • No separate local HTML report — the gated web page is the canonical, cross-device surface.
  • No in-app telemetry SDK — sales reasoning uses App Store Connect aggregates only.
  • No kanban writes — /whh is read-only on the board; /hh remains the sole writer.
