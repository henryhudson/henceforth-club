Design spec · 2026-08-26 · henceforth.club/folklore · status: DRAFT for Henry's review

Reddit for transaction ids

Paste a transaction id. It is a thread. People vote. The winner is paid at the end of the day. Twetch, Treechat, and folklore archives are the same object: sixty-four hex characters on Bitcoin.

What exists. /folklore/tx/<id> already reads a transaction straight from the chain with no index — but it only understands a folklore link/comment JSON blob or a SocialArchive. A Twetch or Treechat post at the same id is notFound(). Submit (/folklore/submit) is built and dark; validateLink demands an https URL. Comments already parent on a transaction id. Elo already folds an append-only duel ledger. Kudos already accrue as earned and markSettled after an on-chain pay. The fifteen-second worker is retired and stays retired. This document is the product that those pieces were waiting for.

The ask. Henry, 2026-08-26: “like reddit but for txids” — after agreeing the board is submit-your-own, Elo-ranked, paid once a day, with a cheap path for what is already on Bitcoin and a dear path for an X export.

Decision 1 — the submission is a target transaction id, not an https URL. The July 19 board was Reddit for web links. This board is Reddit for Bitcoin objects. The paste field accepts a 64-character hex id, or a URL that contains one (folklore's own transaction page, WhatsOnChain, Treechat /t/<id>, an explorer). Extraction is a pure function. A title is required (300 characters, same cap). Optional bound handle by, proved the same way as today (spec C binding over submitMessage). Anonymous remains legal and cannot earn.
Decision 2 — two identifiers, never confused. The target is the transaction being listed (the Twetch post, the Treechat post, the archive). The stamp is the folklore record the submitter broadcasts to pay the floor and claim the listing. The board, the Elo table, the comment parent, and the canonical URL /folklore/tx/<target> all key on the target. The stamp is proof of payment plus title and by. Visiting the stamp's own id shows the record and a link through to the target — it is not a second thread.
Decision 3 — one board row per target. A second stamp for the same target is refused as already-listed (the index write is nx on link:<target>). July 19 allowed duplicate https URLs because two URLs can be the same site; two pastes of the same transaction id are the same object, and Elo cannot sanely duel a post against itself. The first successful stamp owns the row and the kudos earner. Comments all hang on the target, so there is one thread.

1 · The record

Extend the existing folklore link, do not invent a third kind. Legacy https links stay valid forever.

{ "v": 1, "app": "folklore", "kind": "link",
  "txid": "<64 hex target>",
  "title": "…",
  "by": "handle?" }

{ "v": 1, "app": "folklore", "kind": "link",
  "url": "https://…",          // legacy, still parsed
  "title": "…",
  "by": "handle?" }

validateLink accepts a row when the title is in (0, 300] and either txid matches the existing TXID_RE or url is http(s). If both are present, txid is the target. Comments are unchanged: parent is a transaction id — for a listed target, that parent is the target.

The stamp that goes on chain is this JSON in OP_RETURN, plus a payment output of at least the live ten-pence floor to the published revenue address 1GsP511T8e4VjxYdAGnMYdDd6sWxWybcMP (the same address the retired worker paid premium to). Miner fee is the submitter's. No custody, no job, no fifteen-second poller.

Submit is flag-dark today, so there are no production stamp members to migrate. Any future https-only legacy row keeps today's behaviour: member is the stamp id, title links out to url, comments parent on the stamp.

Decision 4 — the submitter signs the stamp. The site never holds a key. The cheap path is not spec B. The visitor (browser wallet or Henceforth) broadcasts the stamp themselves. They POST /api/folklore/index with the stamp's transaction id. The route fetches that transaction, parses the record, checks the revenue output against the live floor, and addLinkToBoard(target, record). If the store is down, the chain still holds the stamp; a retry indexes it. The retired worker is not revived. The dear path (X export) stays the existing archive inscription, still flag-dark, still non-custodial in the app.

2 · Submit

Paste. The field takes a transaction id or a URL. extractTargetTxid(input) (pure, tested) returns 64 hex or null. Case-insensitive hex; output is lowercase.

Preview. The form fetches /folklore/tx/<target>'s parse (or a small GET /api/folklore/preview?txid= that uses the same parser). The submitter sees the card they are listing — Twetch chip, Treechat chip, archive handle, or an honest “on Bitcoin, not a post we can render” with an explorer link. They can still list an opaque id: Reddit does not require that we can iframe the destination.

Title. Required. Default, when the parse has text, is the first line of that text clipped to 300 characters. The submitter may edit it.

Quote. One number: miner fee for this tiny record + ten pence at the live rate, same quoteLink as today. Shown before they sign. The revenue output must meet the floor at index time (live rate). If bitcoin moved between quote and broadcast, a shortfall is refused with floor-short and they can bump and retry; the stamp is not indexed. Documented, not silent.

Sign and broadcast. Wallet in the browser, or Henceforth. Site does not build a job.

Index. On POST /api/folklore/index: target not already listed; record valid; revenue output sufficient; then cache, board, log — existing addLinkToBoard with member link:<target> (today the member is the stamp's id; this spec changes the member to the target).

Decision 5 — the board member is link:<target>. Today's index uses the stamp's transaction id as the member, because the URL was the object. Now the object is the target. Elo postId, comment parent, and the card's permalink all equal the target. folklore:link:<target> caches the validated record (title, by, stamp id). A retry never resets kudos (nx as today).

3 · The reader

/folklore/tx/<id> stays the canonical page. Parse order, first match wins:

  1. Folklore comment → redirect to /folklore/tx/<parent>#<id> (comments have no standalone page, same as July 19 §8).
  2. Folklore link whose txid field is another id (this page is a stamp) → redirect to that target.
  3. Magic Attribute Protocol post (app twetch, treechat, or other Bitcoin Schema type=post) → post card, source chip from app.
  4. SocialArchive JSON → today's profile rendering.
  5. Folklore link with only a legacy url → today's link thread.
  6. Transaction exists but none of the above → 200 with title, short id, explorer link, comment thread. Not a 404. The id is listable.
  7. No such transaction → 404.

The Magic Attribute Protocol parser is pure: script bytes in, a post or null out. Fixtures: one real Twetch transaction, one real Treechat transaction, one hostile/non-post. Media from B-protocol pushes or ordinal outpoints on that transaction, never copied. Source chip: twetch → Twetch, treechat (pin the live app string from the fixture before coding) → Treechat, SocialArchive.source === "x" → X, else folklore.

/folklore ┌─────────────────────────────────────────┐ │ A cello note Twetch │ │ 3 comments · by @henry · elo 1542 │ │ │ │ Kepler's laws X │ │ 1 comment · elo 1500 │ │ │ │ upvalue is just kudos Treechat │ │ 0 comments · by @gavin · elo 1610 │ └─────────────────────────────────────────┘ click row → /folklore/tx/<target> body of the target (parsed) + comments ⛓ explorer

4 · Ranking and money

Two numbers, never mixed:

WhatWhere
EloFeed order. Two listed targets dealt, one tap, applyDuel. Start 1500, K 40 until twenty duels then 16. Undueled sit at 1500. A tap on a row that has no bound by still updates Elo (the table does not need an earner) but pays nobody.kudos:duels fold, sortPostsByElo. Pool = listed targets that parse as arena-eligible (text or media) plus today's archive pool.
KudosThe pot. A paying tap debits the voter's float and accrues earned on the winning row's by. Conservation unchanged: funded = float + earned + settled.Existing float module.
Decision 6 — Elo ranks; kudos pays; the mini settles once a day. A free Elo tap is allowed only if we accept that it moves rank without moving money. Default for v1: a tap is a kudos debit (existing duel debit + cap), so every rank change has a pot. Once a day a launchd calendar job on the mini (not KeepAlive, not fifteen seconds) reads each handle's earned, skips sub-dust (546 satoshis, already a constant), pays the bound address from a dedicated settlement purse, then markSettled. Failure: leave earned untouched, retry tomorrow. No bound address → skip, do not burn the accrual.

Twetch likes and Treechat upvalue do not enter Elo or kudos. They may show on the card as “earned on their chain” when we can read them; they never mint folklore kudos.

5 · The dear path (unchanged)

X is not a transaction id. The visitor's own export is Portable and may be inscribed as SocialArchive. That is the existing archive flow, still flag-dark, still non-custodial in the app. Once inscribed, the resulting transaction id is a target like any other and can be listed cheaply — or the archive inscription itself can be auto-listed as a stamp with title from the handle, so a first archive appears on the board without a second payment. Auto-list is v1: the archive's own transaction is the target; no extra stamp if the archive already paid more than the floor.

Do not fetch Twetch or Treechat from a website and re-inscribe them. Their cheap path is paste (or a later “scan my addresses” that emits target ids into this same submit).

7 · What v1 is not

  • Not a Twetch or Treechat scrape, not JungleBus, not the retired worker.
  • Not re-inscribing on-chain posts, not a blob copy of their media.
  • Not Hodlocker as a named source (the parser will still show a Bitcoin Schema post if type=post).
  • Not https-only links as the main submit (legacy rows still render).
  • Not a free tap that pays winners from Henry's pocket — v1 taps spend float.
  • Not app-side bulk submit of other people's histories (a later “scan my Twetch keys” emits ids into this form).

8 · Tests (behaviour is not shipped until asserted)

  • extractTargetTxid — raw hex, mixed case, folklore/tx URL, WhatsOnChain URL, Treechat /t/, junk → null, two ids in one string → first well-formed 64-hex run.
  • validateLink — txid+title ok; https+title ok (legacy); empty title refuse; both present → target is txid; comment parent still 64 hex.
  • Reader parse order — fixtures: Twetch MAP, Treechat MAP, SocialArchive, stamp that points at a target (redirect), comment (redirect), opaque tx, missing tx.
  • Index — first stamp of a target lists; second is already-listed; short revenue output refused; unsigned by refused; anonymous lists and cannot accrue.
  • Elo — listed target is a DealCandidate with postId === target; two stamps cannot produce two candidates for one target.
  • Quote — floor still ten pence at a live rate; no rate → no quote.

9 · Flags and go-live

FOLKLORE_SUBMIT_ENABLED stays off until: (1) a funded end-to-end of the wallet-signed stamp (real floor paid to revenue, index live, row on /folklore, thread at /folklore/tx/<target>), (2) the Magic Attribute Protocol parser has fixtures from live Twetch and Treechat transactions, (3) a dry run of the daily settler against a test handle. Elo/kudos remain behind KUDOS_ENABLED as today. The archive zip remains behind XFOLKLORE_WEB_ARCHIVE_ENABLED.
