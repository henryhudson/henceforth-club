Design spec · 2026-07-20 · henceforth-club/scripts/board · status: DRAFT for Henry's review

The week plan, in Apple Calendar

The week planner already knows what each day holds and what actually shipped on it. This puts that into a calendar Henry owns, so the plan is wherever he already looks — including his phone — without him opening the board at all.

What exists. The weekly review writes a record per week to Upstash at board:week:<date>. Inside it, retro.weekPlan is an array of days, each carrying a date, a weekday name, an isShipDay or isReviewDay marker, and a list of tasks with a done flag. Separately board:latest holds every kanban card, and cards in the done column carry a doneAt (or movedAt) timestamp. The site renders both at /board/week, behind a cookie gate. As of today there are four week records, twenty-nine planned days, seventy-four tasks, and 115 done cards carrying a date.

The ask. Henry, 2026-07-20: “how about we integrate the board with my apple calendar too… so that i can see on my phone what the plan is etc.” And, when offered a read-only subscribed feed as the alternative: “add it to the calendar that would be best.”

1 · Why events, not a subscribed feed

The obvious mechanism is an iCalendar feed published from the site, which the phone subscribes to and refreshes on its own. It needs no permissions, no agent, and no machine to be awake. It was rejected for one reason: a subscribed calendar is read-only on the device. It arrives as something Henry cannot touch, sitting alongside calendars he owns. He asked for the plan to be added to his calendar, and that is a different thing.

The cost of that choice is stated plainly rather than buried: nothing refreshes by itself. The calendar is accurate as of the last time the sync ran. A subscribed feed would have been self-updating; this is not.

Decision 1 — a dedicated calendar named “Morning Board”, created in the iCloud account. This is the load-bearing choice and everything else leans on it. Because the sync owns that calendar completely, it may create, update and delete inside it without ever reasoning about whether an event is Henry's; visibility toggles with one tick when he wants a clean week; and iCloud carries it to the phone with no work from us. A sync that wrote into an existing shared calendar would have to distinguish its own events from real appointments on every run, and the first bug in that logic deletes something that matters.

2 · Mechanism

A Swift script using EventKit, at scripts/board/calendar-sync.swift, run with swift scripts/board/calendar-sync.swift. It lives beside the existing board tooling (publish.mjs, hh-plan-update.mjs, render-pdf.mjs) because it is the same family of job: read the published board data, emit it somewhere Henry reads.

OptionVerdictWhy
Swift + EventKitChosenThe native path. Fast enough to reconcile a hundred events without noticing, gives real event identifiers for idempotency, and it is the language Henry reads.
AppleScript via osascriptRejectedNo dependencies, but Calendar automation is slow and unreliable at this event count, and it grows worse as history accumulates.
Generate an iCalendar file and open itRejectedPrompts on every import and has no notion of updating an event that already exists, so re-running duplicates everything.
Write to iCloud over CalDAVRejectedNo machine dependency, but needs an app-specific password stored somewhere and the failure modes are hard to reason about.

Swift in a Next.js repository is unusual, and worth one sentence of justification: the alternative is a Node process shelling out to osascript, which is the rejected option wearing a different hat. The script has no build step and no package to install.

3 · Data flow

board:week:* (every week record)  +  board:latest (done cards)
→ group tasks by date, group done cards by doneAt date
→ one PlannedDay value per date
→ reconcile against the Morning Board calendar
→ create, update, or delete

The script reads Upstash over its REST interface using the KV_REST_API_URL and KV_REST_API_TOKEN already in .env.local — the same credentials publish.mjs uses. It reads the published records rather than the local content/board/ files so it cannot drift from what the board is actually serving.

Enumerating weeks is done by scanning for board:week:* keys rather than reading the board:weeks set. Both exist; the key scan is the one proven to return every record.

4 · What an event looks like

One all-day event per planned day. All-day rather than timed, so it sits in the banner row above real appointments and never competes with them for a time slot.

Title — the first task, with a count of the rest. A ship day is prefixed so it is unmistakable at a glance in month view, where the title is all that shows.

Ship day, Deck of Cards 1.26, plus one more
Review column cleared, plus two more
Sci Fri, the weekly science film

Notes — the full plan, then what shipped, then a link back. Rendered in words with no symbols or emoji, per Henry's standing preference.

PLAN
  to do   Ship Deck of Cards 1.26, the free app is the
          only real funnel this week
  to do   Hold Hansard 1.3 as the fallback pick
  done    Correct the store listing long-press line

SHIPPED TODAY
  Deck VoiceOver remaining-count fix
  Register binding hole closed and deployed

https://henceforth.club/board/week
Decision 2 — titles are derived, never stored. The title is computed from the task list on every run. If a task is reworded on the board, the next sync rewrites the title. There is no second copy of the wording to drift.

Title length. Real task labels run long — this week's are between 92 and 250 characters, because they are written for the board where they wrap. A month-view row shows perhaps forty. The first task is therefore truncated to 60 characters on a word boundary, with a trailing ellipsis, before the “plus N more” suffix is appended. The untruncated text is always present in the notes, so nothing is lost, only abbreviated at a glance.

The ship-day marker. Week records carry isShipDay on the day the routine marks for shipping; older records instead carry isReviewDay, which the week page renders with the same emphasis. The sync treats either flag as the ship marker so historical weeks read correctly, and prefixes the title with “Ship day, ”.

5 · Reconciliation

The property that matters: running the sync twice must change nothing the second time. Without it, running from the morning routine every day would multiply events.

  • Fetch every event in the Morning Board calendar across the full span of known weeks.
  • For each planned day, find the existing event whose start date matches. Update its title and notes in place if either differs; leave it entirely alone if they match.
  • Create an event for a planned day that has none.
  • Delete any event in the calendar whose date no longer appears in any week record.

Matching is by date within the owned calendar, not by title or by a marker in the notes. One event per date is an invariant the script enforces: if it ever finds two events on one date, it keeps the first and deletes the rest, because that state can only arise from a bug or from manual editing, and silently tolerating it would hide the cause.

Decision 5 — dates are resolved in the current local calendar, and all-day events are built from date components, never from a parsed instant. The plan stores plain dates such as 2026-07-22 with no time and no zone. Parsing that as an instant yields midnight in some zone, and an all-day event built from an instant lands on the previous day for anyone west of it — the single most common bug in this kind of integration. The script therefore constructs each event's start from year, month and day components in Calendar.current, sets isAllDay, and sets the end to the same day. Matching an existing event to a planned date compares those same components rather than comparing instants.
Decision 3 — a day with no tasks gets no event. Saturdays are frequently empty by design. An event reading “nothing planned” is noise in a calendar, and deleting the event when a day empties is the same code path as deleting a day that left the plan.

6 · Permission

EventKit requires calendar access, granted once, interactively, on first run. This cannot be automated and cannot be done on Henry's behalf. On macOS 26 the relevant entitlement is full access to events; write-only access is insufficient because reconciliation must read existing events to avoid duplicating them.

If access is denied or not yet granted, the script exits with a clear message naming System Settings, and changes nothing. It never degrades to partial behaviour.

7 · Where it runs

On the laptop, at the tail of the /hh and /whh routines, which is where those routines already execute and where the data is already in hand. It is also safe to run by hand at any time.

The Mac mini was considered and rejected: it has roughly ten gigabytes free of four hundred and sixty, runs three continuous-integration workers competing for the machine, and a scheduled agent there would need its own calendar permission grant on a headless login.

8 · Failure handling

ConditionBehaviour
Calendar access deniedExit non-zero naming System Settings. Change nothing.
Upstash unreachable or credentials absentExit non-zero. Change nothing — an empty read must never be mistaken for an empty plan, which would delete every event.
Zero week records returnedTreated as an error, not as an instruction to empty the calendar. Same reasoning.
A single event fails to saveReport which date and continue with the rest, then exit non-zero so the failure is not silent.
The Morning Board calendar is missingCreate it in the iCloud source. If no iCloud source exists, exit with a message rather than falling back to a local calendar that would not reach the phone.
Decision 4 — an empty read is an error, never a deletion. The most damaging thing this script could do is delete a calendar's worth of events because a network call returned nothing. Deletion happens only for dates absent from a plan that was successfully read and contained at least one week.

9 · Testing

The reconciliation decision is a pure function and is tested as one: given the set of planned days and the set of existing events, it returns the lists to create, update, and delete. That function has no EventKit types in its signature, so it runs with no calendar, no permission, and no network.

  • A day present in the plan and absent from the calendar produces a create.
  • A day whose title and notes match exactly produces neither an update nor anything else — this is the idempotency assertion, and it is the one that matters most.
  • A day whose wording changed produces an update, not a delete and a create.
  • An event whose date left the plan produces a delete.
  • Two events on one date produce one delete and the first kept.
  • An empty plan produces no deletions at all.

The EventKit layer around it is a thin translation and is verified by running the sync twice against a real calendar and asserting the second run reports no changes.

10 · Explicitly out of scope

  • Two-way sync. Ticking a task in Calendar will not tick it on the board. Calendar has no notion of a checklist item, and inferring intent from an edited event is guesswork.
  • Alerts and reminders. None are set. An all-day event on a day Henry is already looking at does not need to buzz, and unrequested notifications are the fastest way to get a calendar turned off.
  • The kanban board itself. Only the week plan and the cards finished on a given day. The board is not calendar-shaped and 181 cards would overwhelm the view.
  • Invitations, attendees, travel time, recurrence. Not applicable.
