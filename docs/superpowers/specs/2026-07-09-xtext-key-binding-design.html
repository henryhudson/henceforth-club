Design spec · 2026-07-09 · henceforth.club/x · scope: C of four

The handle you can prove is yours

Bind a key to your X handle while you still control the account, so that when X takes the account, the proof it was yours outlives it — and no one else can claim it in your place.

What exists. The showroom (spec A) shipped: /x shows archives read from Bitcoin and lets a visitor drop their own export. The handle→archive index is a Redis key x:<handle> holding an ordered list of transaction ids, written by POST /api/x/register. That endpoint’s only check today is that the transaction’s inscribed handle string matches the claim — so anyone who knows a handle and any transaction declaring it can register it. There is no notion of who owns a handle, no signature, no per-handle owner or payout address, anywhere on the site.

The one-line thesis: an X account, while it is alive, publishes a commitment to a key it controls; that commitment is captured on Bitcoin inside the ordinary archive; thereafter the account holder proves ownership by signing, not by logging in to X — so the proof survives the account’s death, and the ownership record is a public key the account itself endorsed.

Why now, and why this shape. The naive design — “log in to X and post a code to prove it’s you” — fails at the exact moment the product exists to insure against. The day X suspends you, you cannot log in, so you cannot prove anything; and X recycles handles, so whoever holds @you next could. The fix inverts the timing: you bind the key before the event, while you still hold the account, and prove control after it by holding the key.

1 · The primitives already exist

This is almost entirely wiring. Both sides were surveyed against the real code.

PieceWhere it lives
Identity key m/13'/0'Henceforth app, Wallet.swift — hardened, deliberately isolated from transaction-signing (a nonce-reuse defence its own comment documents), already used to sign air-gap address packs. Its public key is exposed on the wire; its address is derivable.
Sign a challengeBitcoinSignedMessage.sign/verify (the classic Bitcoin Signed Message, base64, address-based) — terminal words SIGN-MSG / VERIFY-MSG. Interop-tested: a signature the app produces round-trips through @bsv/sdk.
Verify a signature on the site@bsv/sdk 2.1.6, already a dependency. PublicKey.verify(msg, sig) and .toAddress(). The site can check a signature and derive an address holding no key of its own.
The holePOST /api/x/register in src/app/api/x/register/route.ts — appends a transaction id to x:<handle> after only a handle-string match.
The trust chain is already wired end to end. The app signs a Bitcoin Signed Message; @bsv/sdk on the site verifies it; there is an interop test proving exactly that round-trip. What is missing is not cryptography. It is the format of the commitment, the gate on registration, and the tick in the interface.

2 · What the tick asserts

The verified tick means, precisely:

“@handle published a commitment to address A on X — here is the tweet, check it yourself — and that commitment was captured on Bitcoin at time T. Address A controls this handle’s archive. The first valid claim wins.”

It is verifiable, not vouched — and the spec says so. Without reading X, no one can cryptographically prove a real account authored the commitment: the archive is self-asserted JSON, so an impostor could inscribe a fake @handle timeline containing a fake binding tweet and sign it with their own key. The site cannot tell a real binding tweet from a fabricated one. Two things bound the damage, and neither is hidden from the user:
  • Delegated checking. The site surfaces the binding tweet’s permalink, exactly as the showroom surfaces a block explorer it does not run. A skeptic opens x.com/<handle>/status/<id> and sees the account really said it. A fabrication has no such live tweet.
  • Bind while alive. The first valid claim wins, and claims are timestamped on Bitcoin. The real owner, acting while their account is healthy — which is the product’s whole advice — wins the race. Against someone who squats a dormant handle first, this is a real limit; the tick’s wording must never overstate past it.
This is the strongest guarantee available without live X reads, and live X reads were rejected by the very problem being solved: you cannot read an account X has already deleted.

3 · The protocol, in three acts

BIND — while the account is alive.
The app shows the owner their identity address A (Base58, about 34 characters), derived from m/13'/0'. The owner posts one tweet, verbatim:
Verifying my Henceforth identity: A — henceforth.club/x
The owner then archives their profile through xtext as normal. The binding tweet is now one of the posts inside the archive, inscribed on Bitcoin at transaction T.
CLAIM — proving it is them.
The app signs the message henceforth-x-register:<handle>:<T> with A’s key, as a Bitcoin Signed Message, and sends:
POST /api/x/register { handle, txid: T, address: A, signature }
VERIFY — on the site, holding no key.
Fetch the archive at T. Confirm a post matches the exact binding format and commits address A. Verify the Bitcoin Signed Message against A with @bsv/sdk. If the handle is unclaimed, this establishes the owner (first valid claim wins). Store the owner record; the tick now renders.

The address A is published (in the tweet) but control requires the private key. Revealing the address lets anyone read the commitment; only the key holder can claim. That is why the public tweet is safe.

4 · Data model (purely additive)

New Redis key x:owner:<handle>, one record per claimed handle:

{ address: string,        // A, the committed identity address
  boundAt: number,        // unix seconds, from the claim transaction's chain time
  bindingTxid: string,    // T, the archive that carries the binding tweet
  bindingPostId: string } // the X post id, so the site can surface the permalink

Binding tweet format — an exact, greppable prefix so parsing is unambiguous:

Verifying my Henceforth identity: <address>

The parser scans the archived posts for this prefix and extracts the Base58 address after it. The trailing — henceforth.club/x is human sugar, not parsed.

Signed message — binds the signature to both the handle and the specific transaction, so a signature can never be replayed onto another handle or another archive:

henceforth-x-register:<handle>:<txid>

Because the commitment is an address, not a public key, verification is Bitcoin Signed Message recovery: @bsv/sdk recovers the public key from the compact signature, derives its address, and compares it to A. No public key need be supplied — the address A from the tweet is the whole input, and this is exactly the round-trip the app’s interop test already covers. The site stores no private key and never has.

The Redis owner record is a rebuildable gate, not the source of truth. The permanent evidence is the binding tweet on Bitcoin. If Redis were lost, an owner re-establishes the record by re-signing — they still hold the key, and the tweet is still on-chain. So the record is allowed to be mutable and off-chain; it gates access, it does not constitute ownership.

5 · Registration gating — the hole, closed

StateWho may register a transaction id to x:<handle>
Unclaimed (no x:owner)Anyone — the showroom principle holds: anyone can archive anyone and populate a handle. Registration stays open, exactly as today, but only to establish content, never to establish ownership.
Claimed (owner A set)Only a registration carrying a valid Bitcoin Signed Message by A. A stranger can no longer append to the owner’s canonical timeline.

A third party’s archive of @handle is always viewable at /x/tx/<txid> — the canonical, index-free view. It simply does not enter a claimed owner’s /x/<handle> feed, and never wears the tick.

Claiming resets the canonical index to the owner’s archive. A handle populated by strangers before its owner claimed could hold junk. On the first valid claim, x:<handle> is reset to the claim transaction T; thereafter only the owner’s signed registrations append. The stranger-inscribed transactions are not destroyed — nothing on Bitcoin can be — they simply leave the owner’s canonical feed and remain reachable by transaction id. This is the owner’s recourse against pre-claim pollution.

6 · The tick

A purely additive prop, threaded ProfilePage → ProfileView and rendered beside the @handle line where the profile header already lives:

verified?: { address: string; bindingPostId: string }

Rendered as a small mark whose hover/tap text is honest — “Bound on-chain. Check the tweet.” — linking x.com/<handle>/status/<bindingPostId>. It is not a blue checkmark cosplay; it is a claim with its evidence one click away. The three /x page components look up x:owner:<handle> at the same call sites that already read the archive index, and thread the prop down.

7 · App side (Henceforth iOS)

Glue over primitives that already exist:

  • A word or affordance to show the identity address A (from the existing m/13'/0' key) and the exact binding-tweet text to copy. The app does not post to X; the user posts it themselves, from the account they are proving.
  • An extension of the existing registerXArchive(handle:txid:) to sign the claim with the m/13'/0' key and include { address, signature } in the POST.

No new key path, no new signing primitive, no new on-chain transaction beyond the archive the user was already making.

8 · Failure modes

SituationBehaviour
Claim with no binding tweet in the archiveRejected — the archive at T contains no post committing A. The owner must post the tweet and re-archive.
Signature does not verify against ARejected — the registrant does not hold A’s key.
Handle already claimed by a different addressRejected — first valid claim wins; the later claim carries no authority over the established owner.
Owner re-archives (a later delta)Accepted with the owner’s signature over the new txid; the binding tweet need not be re-proven, only the owner’s control.
Owner loses the key, account already deadThe handle is frozen — no rebinding is possible without either the key or the live account. Stated plainly: this is the cost of self-custody, and the archive itself is unharmed.
Redis owner record lostThe owner re-establishes it by re-signing; the on-chain binding tweet is the durable evidence.

9 · Definition of done

  • Pure functions, each unit-tested with no I/O: parse a binding address out of an archive’s posts; build and verify the registration message; the claim decision (unclaimed → establish; claimed → require owner signature).
  • The signature verification runs against a fixture signature produced by the app’s Bitcoin Signed Message path — the interop is asserted, not assumed. A key-free fixture; no private key in any test.
  • A test that an unclaimed handle accepts an anonymous registration, and that the same handle, once claimed, rejects an unsigned or wrong-key registration.
  • A test that claiming resets the canonical index and that a pre-claim transaction is dropped from /x/<handle> yet still resolves at /x/tx/<txid>.
  • The tick renders from an owner record and is absent without one; the permalink points at the recorded bindingPostId.
  • Not assertable, and said out loud: whether a real account authored the commitment — that is the skeptic’s click, by design.

10 · Scope — what C is, and is not

C establishes ownership and shows it. The binding, the gated registration, the index reset, the tick. It deliberately stops there.

D is the bounty, and C unblocks it with one value. The address A that C binds and proves is, unchanged, the destination a later archiver’s transaction pays — non-custodial, no escrow, because paying an arbitrary owner address is identical in shape to the reward payout xtext already makes. C stores A; D spends to it. Nothing in C needs to anticipate D beyond keeping A exactly as it is: an address, publicly committed, provably controlled.

Not in C: any bounty routing, any escrow, any second on-chain binding record (the tweet is the record), and any live X read (the permalink is the check).

11 · Open questions

  • Address format in the tweet. A bare Base58 address is greppable but featureless; a light prefix or checksum tag could reduce the chance a parser mistakes an unrelated address in someone’s post for a binding. The exact regex is a plan-level decision; the format must be pinned before the app ships copy that users paste.
  • Rebinding while alive. An owner who wants to rotate keys posts a new binding tweet and re-archives; the site takes the latest account-authored binding as authoritative. The precedence rule (latest-wins among the owner’s own bindings, but first-wins across different claimants) needs stating precisely in the plan so a rotation cannot be used to hijack.
  • Legal, deferred to the same lawyer as spec A. A verified tick asserting a person controls a handle edges toward an identity claim; the wording should be reviewed alongside the archival-permanence questions spec A already raised.
