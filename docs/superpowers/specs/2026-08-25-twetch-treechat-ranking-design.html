Design spec · 2026-08-25 · henceforth.club/folklore · status: DRAFT for Henry's review

One board, satoshis given

Twetch and Treechat posts are already on Bitcoin. Folklore ranks by satoshis paid. The work is a mapper and a scan, not a third social network.

What exists. Folklore reads SocialArchive JSON from Bitcoin and ranks a post by satoshis given (foldScores — founding / upload cost is ledgered and excluded from the rank). The launchd worker is dead. The web archive flag is dark. Inscription stays in Henceforth. Twetch.com shut in June 2024; the posts remain as Magic Attribute Protocol records, app=twetch type=post, usually signed with the Author Identity Protocol, media often on the same transaction via the B protocol. Treechat writes the same Bitcoin Schema (type=post) and already resurrected Twetch and Hodlocker into its own client. Treechat ranking is upvalue: a micropayment to the post. That is folklore kudos under another name.

The ask. Henry, 2026-08-25: “it would be good we need the data from twetch and treechat ideally so we can rank them.” And the standing lean rule from the same morning: Bitcoin and the mini, no Redis poller.

Decision 1 — rank is satoshis paid to the post. One number, one fold, every source. A folklore kudos, a Twetch like, and a Treechat upvalue are the same event: bitcoin sent that names a post transaction. Do not mix miner fees or inscription cost into this board — old Twetch posts would win by being expensive to write, not by being valued. The existing class floors (video before photo before text) may still break ties when a post has no payments.
Decision 2 — point, do not copy. Each post's identity is its original transaction id. Folklore does not re-inscribe Twetch or Treechat text, and does not copy media into a blob store. The reader resolves media from the source transaction (B protocol / ordinal outpoint). Re-wrapping as SocialArchive is allowed later as an optional bundle; it is not required to rank.
Decision 3 — no daemon. Twetch is a finite historical scan (the app is dead). Treechat is a live app; a JungleBus or 1sat lookup on demand is enough until volume proves otherwise. The mini may run a one-shot ingest. The retired xtext-worker stays retired.

1 · One post, three apps

Bitcoin Schema already is the shared shape. A post on chain looks like:

OP_RETURN
  B <text or file> <media-type> utf-8
  | MAP SET app twetch|treechat type post [paymail …]
  | AIP BITCOIN_ECDSA <address> <signature>

Folklore's own archives are a fourth encoding (SocialArchive JSON) of the same idea: handle, posts, media outpoints. The mapper's job is to turn any of these into one in-memory post:

{ id: txid,          // original transaction, never a new one
  source: "twetch" | "treechat" | "x" | "folklore",
  at, text,
  author: aipAddress | paymail | handle,
  media: [{ outpoint, kind }],
  parentTxid? }

SocialArchive.source is already a free string. No wire change for wrapping. The ranking table is keyed by id (the transaction id), which is how sortPostsByScore already sorts.

2 · One vote

A vote is a later transaction that pays satoshis and names a post:

AppOn chainWeight
Folklore kudosExisting vote ledger (funding transaction id, post id, satoshis)satoshis paid
Twetch likeMAP type=like with tx = post transaction, plus a payment outputsatoshis paid to the author (not the like's miner fee)
Treechat upvalueMicropayment that references the post; MAP type to be pinned against one live Treechat transaction before codingsatoshis paid

The fold is foldScores as it stands: sum of signed satoshis per post id, founding entries excluded. A Twetch like becomes a VoteLedgerEntry with txid = the like transaction, postId = the liked post, sats = value paid. Replayable, no cache of the number.

3 · Ingest

Mapper (pure). Magic Attribute Protocol bytes in, post or vote out, or null. One fixture: a real Twetch post transaction. One fixture: a real Treechat post transaction. One fixture: a Twetch like. No network in the mapper.

Twetch scan (finite). On the mini, once: walk JungleBus / WhatsOnChain history for app=twetch type=post and type=like. Write a local JSONL of mapped posts and votes (gitignored, like the board). Twetch will not grow.

Treechat scan. Same mapper, filter app to Treechat's published app name (pin from a live post before coding — do not guess). First pass can be Henry's own addresses plus a named list (the Craig Wright seed card is this list). Full-network scrape is a later decision; it is a million-transaction job and is how Treechat themselves did Twetch.

Show. Folklore feed reads the JSONL (or an inscribed manifest of transaction ids) and the vote fold. Redis is not the source of truth. If the site needs a hosted copy, inscribe the index (transaction id list + vote list), not the posts.

4 · Identity

Twetch users are paymails / usernames in MAP, signed by an AIP address from the Twetch seed family Henceforth already derives (m/0/0 and payment chains). Treechat users are the same schema. Folklore users are bound X handles. Do not invent a new identity. Display whatever MAP carries; ranking does not need a handle at all (it keys on post transaction id).

Henry's own Twetch archive is the first ingest: the app already knows the address family. Other people (Craig Wright) need a named address or paymail on the seed list, not an X API pull.

5 · What this is not

  • Not a live Twetch clone, not a Treechat client, not a JungleBus subscription that ticks forever.
  • Not the kudos float, Elo arena, or web-archive job machine.
  • Not Hodlocker in version one, though it is the same protocol and can ride the mapper later.
  • Not re-hosting video. Original outpoints or it does not show.

6 · Open questions

  • Q1. Rank by earned satoshis only (recommended, Decision 1), or also add original post value as founding? Treechat's own ranking is earned only.
  • Q2. First ingest: Henry's Twetch only, or the named seed list (Craig Wright and friends) in the same pass?
  • Q3. Treechat live updates: on-demand lookup when someone opens folklore, or a daily mini scan?
  • Q4. Pin one live Treechat post and one upvalue transaction as fixtures before the mapper is written — Henry or a public Treechat URL.

No money path in this spec. The mapper is pure. Ingest is a scan. Ranking is a fold over payments already on chain.
