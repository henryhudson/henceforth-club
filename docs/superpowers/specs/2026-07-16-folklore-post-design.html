Design spec · 2026-07-16 · henceforth.club/folklore · status: DRAFT for Henry's review

The post that outlives its platform

A compose box on folklore: write once, and the words land on Bitcoin first and on X second. The chain is the record; X is the distribution. Nothing here is built yet — this document exists to be argued with.

What exists. Folklore reads archives from Bitcoin and ranks posts by committed satoshis — upload cost plus earned votes, live as of today. The web archive machinery from spec B is built and tested behind its go-live flag: /api/folklore/job accepts work, a Mac mini worker holds a per-job key for minutes, inscribes, and sweeps the remainder to revenue. The app archives whole profiles non-custodially. What nobody can do yet is write a new post from folklore itself.

The ask. Henry, 2026-07-16: “we probably also need a post button — this should be able to post on folklore and x.”

1 · What a folklore post is

A folklore post is text inscribed to the author's archive on Bitcoin, appearing in their /folklore/<handle> feed and the ledger, carrying a founding cost like any archived post. Cross-posting to X is an option on top, not the substance: if X refuses, rate-limits, or dies, the folklore post still exists. That ordering is the product's whole thesis said back to it.

Decision 1 — the chain is primary. A compose is an inscription job first. The X copy is best-effort distribution, marked on the folklore post when it succeeds (“also on X” with the X post id). We never block permanence on a platform's availability.

3 · The flow

Compose — a text box on /folklore (owner-only), 280-character soft guide but no hard X limit; text only in phase 1. A live quote shows the inscription cost in sats and pounds, the same quote machinery the archive drop zone uses.

Pay — the spec B rails verbatim: the compose creates a job, the QR asks for the quoted amount, the worker watches, inscribes on confirmation, and sweeps. Henry's phase 1 alternative: pay from the app wallet against the same job id, skipping the QR.

Inscribe — the worker writes the post using the archive's existing OP_RETURN schema with a fresh post id, appends the founding vote at inscription time (the lesson of today's ranking gap: costs are recorded when the money moves, never backfilled), and invalidates the archive cache so the post appears within a minute.

Cross-post — if the author ticked “also post to X”: after the inscription confirms, the worker calls X's create-post endpoint with the author's OAuth token. Success stamps the folklore post with the X id; failure marks the job x-copy-failed, visibly, with retry. The inscription does not wait for X.

Decision 2 — inscribe first, X second. The alternative (X first, inscribe its returned id) makes the archive mirror X's record, which is the old world's ordering. Here the post id is ours; the X copy carries a link back to henceforth.club/folklore/<handle>. Folklore is the original; X gets the copy.

4 · The X write integration, honestly

  • Auth: posting as a user requires OAuth 2.0 user-context tokens with tweet.write scope. Phase 1: a one-time authorization of Henry's own account, refresh token held server-side in .env.local/Vercel env — the same trust level as the existing shared-token fetch path. Phase 2 needs a real OAuth flow and token store per verified handle.
  • Cost and quota: write quotas differ by API tier and have changed repeatedly; xtext already learned X's pricing the hard way (reads billed per post). Open question 1: verify the current write quota on the account's tier before building — do not assume.
  • Policy: posting the user's own words with their own authorization is the cleanly permitted direction (unlike bulk reading). The 280-character limit and media rules apply to the X copy only; folklore itself has no such limits.

5 · Money and custody

Identical posture to spec B, because it is spec B: the per-job key exists for minutes, holds only that job's payment, refuses to overwrite a published key, and sweeps to revenue. A compose job is smaller and cheaper than an archive job — one short inscription. The founding vote is appended by the worker inside the job, with the actual fee paid, split across exactly one post: no estimation, no backfill.

6 · Failure modes

FailureBehaviour
Paid, inscription failsSpec B's existing retry/refund posture; the job state page tells the truth
Inscribed, X copy failsPost exists on folklore, marked “X copy failed · retry”; never silent
X token expiredCompose still works with the X tick disabled and a “reconnect X” note for the owner
Double submissionJob ids are idempotent; the same compose text within one job cannot inscribe twice

7 · What phase 1 is NOT

  • No media in the compose (photos and videos ride the media-attribution work, separately designed).
  • No multi-user OAuth — the witness account only, gated by the board session.
  • No replies/threads composed from folklore — standalone posts first.
  • No public compose — the box renders for the signed-in owner, invisible to visitors.
