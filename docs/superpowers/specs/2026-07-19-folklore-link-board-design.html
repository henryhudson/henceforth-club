Design spec · 2026-07-19 · henceforth.club/folklore · status: DRAFT for Henry's review

Reddit for bitcoin links

Folklore stops being an archive with a feed and becomes a board with an archive on it: anyone submits a link, the community gives kudos, the front page is whatever the kudos say it is — and every entry on the board is a Bitcoin transaction.

What exists. Folklore reads archived X profiles from Bitcoin, ranks the feed by kudos alone (upload cost was dropped from the score on 2026-07-18), runs Elo duels for videos in the arena, and holds the spec B custodial rails behind their flag. The Upstash index (x:handles, per-handle txid lists, the score and vote families) tells the site which transactions to read; WhatsOnChain serves the bytes; the OP_RETURN JSON parser in onchain.ts turns them back into posts.

The ask. Henry, 2026-07-19: “with folklore it would be good if it was like reddit but for bitcoin links” — and, on the data: “it will be a list of txids as we do. i also think in the henceforth app we should create a file called folklore when we make an account — this can contain all the txids and should have the date of last sync so we dont need to fetch loads of data meaninglessly.”

1 · The reframe

Folklore is the board. An archived X profile is one kind of submission; a link is another; both live in the same kudos-ranked feed. Nothing about the archive changes — it simply stops being the whole product and becomes the founding content of a larger one.

Decision 1 — one board, one ranking. Links and archives share a single feed ordered by kudos total, exactly the ranking that exists today. No hot algorithm, no time decay, no tabs. If old links pinning the front page becomes a real problem, that is a good problem, and a later spec.

2 · What a submission is on-chain

Two new OP_RETURN JSON record kinds beside SocialArchive, written and parsed by the same pushdata machinery:

{ "v": 1, "app": "folklore", "kind": "link",
  "url": "https://…", "title": "…", "by": "handle?" }

{ "v": 1, "app": "folklore", "kind": "comment",
  "parent": "<txid of the link>", "text": "…", "by": "handle?" }
RuleValueWhy
Title cap300 charactersReddit's own limit; long enough for any honest headline
Comment cap10,000 charactersAn essay fits; a novel pays for its own archive instead
URL schemehttp(s) onlyRenderable in every client; no javascript:, no surprises
byOptional bound handle (spec C binding)Attribution when claimed and verifiable; anonymous stays legal
DuplicatesAllowed in v1Resubmission costs sats again; the fee is the dedupe
Decision 2 — the chain is the record, the index is an opinion. Any client can re-derive the whole board by scanning for these records. The Upstash index is how our site and app find them quickly; it is curation, not custody of truth.

3 · The board index (Upstash)

KeyShapePurpose
folklore:boardSorted set: txid → kudos totalThe front page is one ZRANGE. Seeded from the existing archive directory and its scores.
folklore:comments:<txid>List of comment txids, oldest firstThread rendering on a link's page
folklore:logSorted set: txid → index-insertion time (ms)Delta sync for the app's folklore file — every board and comment txid lands here when the index learns of it

Kudos keep the existing score and vote machinery unchanged; a kudos event additionally bumps the txid's score in folklore:board so ranking stays a read-time no-op.

Decision 3 — the sync clock is index-insertion time, never block time. A transaction indexed late (a backfill, a re-scan, someone else's old inscription adopted onto the board) must still reach every client whose watermark postdates its block. The log records when we learned of it; that is the only clock a since query can be honest against. This is the since_id lesson of 2026-07-16, applied on purpose.

4 · The site

Feed — /folklore renders the unified board from folklore:board. Archive entries keep their card; a link entry shows title, domain, submitter (when bound), kudos, and comment count.

Link page — the existing per-transaction page grows a thread: the link, then its comments from folklore:comments:<txid>, each rendered from chain.

Submit — /folklore/submit: url + title + optional comment, live sat/pound quote from the folkloreJob quote machinery, then the spec B rails verbatim — pay the quoted amount, the worker inscribes the record, broadcasts, writes the txid into folklore:board and folklore:log. Ships behind its own flag until the rails have carried Henry's own money end to end.

Sync endpoint — GET /api/folklore/index?since=<ms> → { "txids": […], "now": <ms> }: every txid whose log score exceeds since, ordered by insertion, plus the server's own clock for the client to store as its next watermark. since=0 is the first sync and returns everything.

Giving kudos remains Henceforth-only (the 2026-07-18 call, unchanged): the web reads and submits; the app votes.

5 · The Henceforth app

Two new words in the folklore vocabulary, paying from the user's own wallet, non-custodially, the way the archive already does:

s" https://…" s" title" folklore-post     \ inscribe a link, txid on the stack
s" <txid>" s" text…" folklore-comment    \ inscribe a comment under a link

The folklore file. Created alongside the account, one JSON document:

{ "v": 1, "lastSyncAt": 0, "txids": [] }

Opening the board runs one delta fetch — /api/folklore/index?since=lastSyncAt — appends the new txids, and stores the server's now as the new watermark. Transaction content is fetched per-txid only when a row scrolls into view, and cached; the file guarantees the app never re-downloads the list, and the lazy fetch guarantees it never downloads bodies nobody looked at. That is the “no meaningless refetching” requirement, made of two small parts.

Decision 4 — the watermark is server-stamped. The client never derives lastSyncAt from its own clock or from the data; it stores exactly the now the server returned, the same clock the log is scored by. Device skew cannot open a gap. The merge (file + delta → file) is a pure function with its own tests.

6 · Money and custody

Nothing new. The app path is non-custodial — the user's wallet signs and broadcasts, as with archives. The web path is the spec B posture verbatim: per-job key alive for minutes, holds one job's payment, sweeps to revenue. A link inscription is the smallest job the rails will ever carry. The adversarial money-path review gates any build task that touches payment code — this document is the thing to attack first.

7 · Moderation, honestly

The chain is immutable; the board is curated. Delisting removes a txid from folklore:board and from all future folklore:log deltas — the site stops showing it and new syncs never learn of it. Files that already hold the txid keep it forever; when such an app fetches the content the site simply serves nothing, and the row renders as unavailable. This is the only lever that exists if someone inscribes something unlawful, and the spec says so out loud rather than pretending otherwise.

8 · Failure modes

FailureBehaviour
Paid on web, inscription failsSpec B's existing retry/refund posture; the job page tells the truth
Comment whose parent is not on the boardIndexed into the log (sync is complete) but rendered nowhere until its parent exists; never an error
Malformed or hostile record on-chainFails the shape check in the parser and is invisible, exactly as a garbage SocialArchive is today
Oversized title/comment at submitRefused before payment, both app and web; caps live in one shared constants module per side
Sync response lost mid-flightWatermark unchanged, next sync refetches the same delta; merge is idempotent (txid set union)
Duplicate submission of the same URLTwo board entries, each having paid; v1 accepts this

9 · Testing

  • Site (vitest, test-first): link/comment record encode and parse beside the onchain.ts suite; since filtering and ordering of the log; board seeding from the existing directory.
  • App (Swift Testing, test-first): the folklore file's read/write round-trip; merge(file, delta) → file as a pure function — union, watermark adoption, idempotence under replayed deltas; word-level submit builders against fixtures, key-free as always.
  • Behaviour isn't shipped until asserted; the one genuinely manual step is the first real-money submit on each path, which follows the funded-run standard (fresh build on Henry's phone, live monitoring).

10 · What v1 is NOT

  • No hot/new/top tabs — kudos total only (Decision 1).
  • No kudos on comments — kudos rank board entries; threads are flat and chronological.
  • No URL dedupe, no media on links, no notifications, no subreddit-style sections — one board.
  • No app-side chain scanning — the app syncs from the index (Decision 2 keeps the trustless door open for anyone who wants to walk through it later).
