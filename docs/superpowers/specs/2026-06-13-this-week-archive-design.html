This Week in Parliament — Archive Browse phase 1.1

2026-06-13 · design spec · Redesign of henceforth.club/hansard/this-week from a flat list into a findable archive: the 4 most recent issues as a hero, then a year-of-weeks calendar with text search. Follow-up to 2026-06-03-this-week-in-parliament-design.html (the generation pipeline) and the archive-index commit 8897428 (which made the bare URL a directory of permalinks).

One-line summary: the archive page becomes three stacked zones — a hero (newest issue large + the prior 3 small), a year-of-weeks calendar (one cell per ISO week, recess weeks amber, hover → headline, click → permalink, switch years), and a client-side text search that dims non-matching weeks. The server reads the filesystem and projects each digest to a thin DigestSummary for the client; the calendar layout and the search predicate are pure, unit-tested functions.

Why a calendar, not a grid. The data has exactly one issue per ISO week — a regular time series, not an unordered pile. A grid treats 52/year as a list to mitigate with filters; a week-calendar treats it as what it is, and earns a domain story for free: the parliamentary recesses (summer, conference, Christmas) render as amber runs, so the rhythm of Parliament becomes the navigation. Search is the one general-purpose escape hatch on top, not the primary finder.

1 · Goals & non-goals

Goal. Make a year's worth of weekly issues findable from /hansard/this-week without an endless scroll: surface the recent run prominently, let a reader navigate the back-catalogue by time at a glance, and give them a search box for the one case time-navigation doesn't cover ("where did they discuss X?"). Keep the page fast (static hero, small client payload) and on-brand (the existing parchment/stone/emerald palette).

Non-goals. No change to permalinks, OG cards, DigestView, the cron, or generation. No server-side search index or pagination API — search is client-side over the in-memory summaries (the dataset is small and bounded). No semantic topic classification beyond the topTopics the digest already carries. No accounts, comments, or analytics. No multi-select faceting (topic chips were considered and deferred — YAGNI).

2 · Page architecture

The page stays a server component — it reads the filesystem, so it cannot be a client component. It does the read once, projects to summaries, splits off the recent 4, renders the hero server-side (static HTML, no JS), and hands the full summary array to a single client island for the interactive calendar + search.

  /hansard/this-week  (server component, revalidate 3600)
        │  listPublishedSummaries()           ← fs read + projection (pure-cored)
        │  split: recent4 = summaries[0..3], all = summaries
        ▼
  ┌─ RecentHero  (server, static) ──────────────┐
  │   hero(newest) + 3 small cards → permalinks  │
  └──────────────────────────────────────────────┘
  ┌─ ArchiveCalendar  (client island) ──────────┐
  │   search box  →  matchesQuery(summary, q)     │  pure predicate
  │   year switch →  calendarByYear(all)[year]    │  pure layout
  │   week cells  →   to /this-week/{week}  │
  └──────────────────────────────────────────────┘

The split keeps the heavy, static part out of the JS bundle and confines interactivity to the one component that needs it.

3 · Components

_components/RecentHero.tsx server

Takes the 4 most recent summaries. Renders the newest as a large card (window label, headline, intro/feature line) and the next 3 as a compact row. Pure presentational; no state. Degrades correctly when fewer than 4 issues exist (renders what there is).

_components/ArchiveCalendar.tsx client

Holds the search string and selected year in useState. Renders the search input, the year switcher (when >1 year), and the week grid for the selected year. Each published cell is a next/link to its permalink with the headline as its accessible label / tooltip. When the query is non-empty, cells failing matchesQuery get a dimmed style; matching cells keep full contrast. No data fetching — everything is derived from props via the pure helpers.

4 · Data layer (pure seams)

Added to src/lib/this-week/. Each is a total function over plain data, unit-tested without a DOM or filesystem.

  • DigestSummary (in types.ts): { week, windowLabel, headline, mode, topics: string[], feature: string | null }.
  • toSummary(d: DigestData): DigestSummary — the projection. topics from topTopics.map(t => t.heading); feature from feature?.title ?? null; headline from headline ?? windowLabel.
  • listPublishedSummaries(): DigestSummary[] — listPublishedDigests().map(toSummary) (newest first). The only fs-touching addition; thin wrapper over the existing store read.
  • calendarByYear(summaries): YearCalendar[] — groups by the calendar year of week and places each issue at its ISO-week index (1–53), London-aware to match window.ts. Returns years newest-first, each with a fixed-length cell array (present weeks carry their summary; absent weeks are empty). Month boundaries derived for labels.
  • matchesQuery(s: DigestSummary, q: string): boolean — case-insensitive substring over headline + topics + feature. Empty/whitespace query returns true (everything matches).

5 · Calendar & search behaviour

Cells. Sitting issue → emerald; recess issue (mode === 'recess') → amber; no issue → faint neutral, non-interactive. Hover/focus reveals the headline (native title + visually-hidden text for SR); click navigates to the permalink.

Search. Typing filters via matchesQuery; non-matching published cells drop to a dimmed style (they stay in place — the calendar shape is the point — they just recede). A small count ("7 of 52 match") gives feedback. Clearing the box restores full contrast.

Year switch. Prev/next (and/or a select) move between years from calendarByYear; search persists across the switch so a query spans the whole archive visually.

6 · Error & empty states

  • Zero published issues → notFound() (unchanged from the current page).
  • Fewer than 4 issues → hero renders what exists; calendar shows the single (current) year, switcher hidden.
  • A draft/missing week → already excluded upstream by listPublishedDigests; the calendar never links a non-published cell (the same 404-avoidance the archive-index commit established).

7 · Testing

Swift-free; vitest over the pure functions — the load-bearing logic, asserted without a DOM.

UnitAssertions
toSummary / listPublishedSummariesProjects exactly the summary fields; headline/feature fallbacks; topics mapped from headings; order preserved (newest first).
calendarByYearCorrect year grouping; week placed at the right index; year-boundary cases (late-Dec vs early-Jan); a 53-week year; absent weeks empty.
matchesQueryCase-insensitive headline hit; topic hit; feature hit; empty/whitespace query matches all; non-match returns false.

Interactivity (dim on no-match, hover headline) is a thin render over matchesQuery, so the predicate test is the behavioural assertion. A component/snapshot test is out of scope for v1 unless the calendar render proves fiddly.
