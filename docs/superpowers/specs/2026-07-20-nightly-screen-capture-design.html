Design spec · 2026-07-20 · Mac mini · status: DRAFT for Henry's review

Nightly screen capture

Photograph every reachable screen of one app each night, keep only what changed, and put that in front of Henry each morning — without ever risking the three continuous-integration runners that share the machine.

The ask. Henry, 2026-07-20: “can you ensure the screenshots are rerun on the mac mini each night? then we can review the state of the app properly.”

Why it is worth building. The screenshots that exist are from 2026-06-01, seven weeks stale, and were only found to be stale because a back-button question forced someone to look. An app changes every day and nobody sees the accumulated drift until it is large. A nightly capture makes drift visible while it is still one screen wide.

1 · What exists, and what it costs

AppCapture pipelineOn the mini?
HenceforthScripts/regenerate-snapshots.sh — 204 screens, every reachable oneNo — only inside the continuous-integration runner's workspace
Deck of CardsScripts/regenerate-snapshots.sh — every reachable screen, plus paired multiplayerYes, at ~/Programming/Main Projects/
HansardNone. Two capture flows feeding the App Store listing, no design boardYes

The machine has roughly ten gigabytes free of four hundred and sixty, and three continuous-integration runners share it. Simulator devices hold nineteen gigabytes, but the five largest account for 17.7 of that and every one is in active use, so the space is not meaningfully reclaimable. A measured Deck capture consumed about 3.3 gigabytes.

Decision 1 — one app per night, alternating, never all three. This is what makes the whole thing fit. Only one app's build artifacts exist at any moment, and they are deleted when that app finishes. Running three apps nightly against ten free gigabytes would eventually exhaust the disk, and the cost of that is not a missing screenshot — it is all three continuous-integration runners failing at once, which is strictly worse than having no nightly capture at all.
Decision 2 — Henceforth and Deck only; Hansard gets a card, not a bolt-on. Hansard has no design board, so it cannot answer “what does every screen look like” at any price. Including it with its two App Store capture flows would produce a night that looks like coverage and is not — that night would never have surfaced the back-button drift, because those flows never open a settings, detail or modal screen. Building Hansard a proper board is its own piece of work. Noted honestly: Hansard is the app with zero ratings, so it is arguably the one most worth seeing, which is an argument for doing that work soon rather than for faking it now.

2 · The schedule

Monday, Wednesday, Friday — Henceforth
Tuesday, Thursday, Saturday — Deck of Cards
Sunday — nothing

Three nights each, at 03:00, which is when the runners are quiet and the daily review pipeline has not yet started (it pulls at 04:00). A launchd agent, matching the dozen already on that machine — the daily review pull and send, the text monitor, the xtext worker, the three runners. Nothing new is introduced mechanically.

3 · The three guards

Most of this design is refusals. The capture itself is an existing script; what is new is everything that stops it doing harm.

Decision 3 — a disk floor, checked before anything is built. If free space is below six gigabytes, the run does not start. It records that it skipped and why, and exits. Six is chosen because a measured capture costs about 3.3, so the floor leaves the machine unable to cross into the region where a runner's own build would fail. A skipped night is a small loss; a full disk is three broken runners and a morning spent diagnosing it.
Decision 4 — a continuous-integration interlock. If a runner job is active, the capture does not start. Both want simulators, the machine has one shared device set, and Henceforth's interface tests are already flake-prone enough to be a tracked card. Three in the morning is usually quiet, but usually is not a guarantee, so it checks rather than assumes.
Decision 5 — artifacts are deleted as part of the run, not after it. Build output is removed when the app finishes capturing, inside the same script, so a crash between apps cannot leave two sets on disk. This is the difference between a rotation that fits and one that slowly does not.

4 · Baselines, and why nothing is committed

The two apps disagree about git, which rules out the obvious approach. Deck commits twenty-four snapshots so its --baseline <sha> diff can git show them. Henceforth gitignores all two hundred and four deliberately. There is no common baseline to diff against.

Committing nightly would be worse than inconvenient: two hundred and four images at roughly two hundred kilobytes is about forty megabytes a night, over a gigabyte a month, into repositories currently seventy-two and one hundred and sixteen megabytes.

Decision 6 — the baseline lives beside the capture on disk, and nothing is committed. Last night's set is kept as snapshots-baseline/; the new capture lands in the pipeline's usual directory; changed screens are found by comparing file hashes. Deck's existing --baseline diff mode is untouched and keeps working — this is an additional on-disk baseline, not a replacement for it.

5 · How it reaches Henry

Two hundred and four images is not something a person reviews. Six named screens is.

Each run writes a status file recording the date, the app, how many screens were captured, which changed, and if it did not run, why. The morning routine reads that file and reports it, then copies the changed images to the laptop for actual looking.

OVERNIGHT: Henceforth, 204 screens captured 03:04
  6 changed since Friday:
    wallet-detail, settings-appearance, terminal-vocabulary,
    send-many, xarchive-sheet, file-editor
  pulled to ~/Desktop/overnight/ for review

A quiet night reads OVERNIGHT: Henceforth, no screens changed. — which is information, not an absence of it.

Decision 7 — a stale or missing status file is reported loudly, as a failure. This is the decision this spec cares most about. A nightly job that quietly stops running is worse than no job, because it manufactures false confidence: Henry would believe he had coverage he did not have. The morning routine therefore treats an absent or out-of-date status file as a finding in its own right, not as silence. This is not hypothetical — on this same day a fix shipped whose failure path renders to the user as “on-chain, site indexing pending”, so a permanent failure reads as success. The same shape, caught here before it is built rather than after.

6 · Failure handling

ConditionBehaviour
Free space below six gigabytesSkip. Record the reason and the measured figure. Exit zero — a deliberate skip is not a failure.
A continuous-integration job is runningSkip. Record which runner. Exit zero.
The capture script failsRecord the failing app and the last output. Delete artifacts anyway. Exit non-zero.
Capture produces zero imagesTreated as a failure, never as “every screen was deleted”. The baseline is left untouched so the next run still has something to compare against.
The repository will not updateCapture the existing checkout anyway and record that the code is stale, rather than skipping. A picture of last week's code beats no picture.

7 · What has to be set up once

  • Henceforth cloned to the mini at ~/Programming/Main Projects/Henceforth, matching where Deck and Hansard already sit. One hundred and sixteen megabytes of history. It must not use the continuous-integration runner's workspace, which a live job may check out or clean underneath it.
  • Its snapshot pipeline verified once by hand before it is scheduled. A pipeline that has never run on that machine should not first run unattended at three in the morning.

8 · Explicitly out of scope

  • Hansard. Carded, not bolted on. It needs a design board built properly.
  • Automatic judgement of what changed. The run reports which screens moved; deciding whether a change is an improvement is Henry's, and a machine guessing would train him to ignore it.
  • Publishing images to the board. No board surface renders images today, and building one is its own piece of work. The changed screens land on the laptop instead.
  • Committing screenshots. Covered above — the repository cost is not worth it.
