Design spec · 2026-07-30 · henceforth.club/board/ledger · status: DRAFT for Henry's review

A ledger that can prove itself

Henceforth Bitcoin Limited's accounts move off a spreadsheet and onto a gated page, and every accounting period ends with a Merkle root on chain. The bookkeeping is the excuse; the commitment primitive is the point.

What exists. ~/Henceforth/ANNUAL ACCOUNTS.xlsx held four year-sheets and 96 transactions running 2022-01-06 to 2025-07-03. On 2026-07-30 those were converted to a flat, reconciled ledger at ~/Henceforth/ledger/transactions.csv, with check.py to validate edits and summarise.py to cut totals by period. Every sheet reconciled exactly against its own stated total. The spreadsheet is now a frozen historical record.

The ask. Henry, 2026-07-30: “lets make it a web app and ensure it is able to be uploaded to bitcoin this can be the begining of our scripted supply journey”.

Decision 0 — the ledger does not go on chain. Its hash does. “Uploaded to Bitcoin” read literally means publishing the company's bank accounts, vendors and amounts permanently and publicly. Scripted Supply's own page already rejects that pattern — “Encrypted payloads live off chain; only their SHA-256 hash is committed on chain” — and the reasoning applies harder to accounting records than to purchase orders. A commitment buys tamper-evidence and provable existence at a point in time, which is exactly what an accounting record wants. Publication buys nothing and cannot be undone.

1 · Why this is not merely bookkeeping

The Scripted Supply research notes name the differentiator plainly: a legible contract that compiles byte-for-byte to the Script the chain enforces, hash-commit rather than payload-on-chain, local-first rather than server-and-SQL. Nothing in that thesis has yet been built as working web software. The supplier portal is described as greenfield.

A company ledger is the smallest honest instance of the same shape: a set of records held privately, committed publicly, and later proved selectively to a third party who must not see the rest. Build that once here and a purchase order commits by exactly the same path.

2 · The three decisions taken

Decision 1 — a gated route on henceforth.club, data in Upstash. Chosen over local-first storage. The trade-off was raised and accepted: the company's transaction history sits on hosted third-party infrastructure rather than only on Henry's machine. What it buys is entry from any device, which matters because the binding constraint on this project is typing, not architecture.
Decision 2 — a Merkle root per accounting period. Chosen over a single snapshot hash and over a per-save hash chain. Each transaction is a leaf, so a single transaction can later be proved to have been in the filed set without disclosing the other ninety-five. Selective disclosure is the property Scripted Supply needs for purchase orders, so it gets built once, here.
Decision 3 — server-side broadcast reusing the board archive key. Chosen over signing in the Henceforth app and over a browser-held key. The pattern already works in this repository at scripts/board/render-pdf.mjs:81. Roughly four transactions a year at fractions of a penny each. The key stays in Henry's .env.local and is never handled in conversation.

3 · Route and gate

/board/ledger, inside the existing gated board world. It reuses src/lib/board-auth.ts and the board_session cookie, so no new authentication surface is written and none can be got wrong. Data lives in Upstash under ledger:* and is never committed, matching the discipline already applied to board:latest.

KeyHolds

4 · The record

The shape is deliberately identical to the CSV columns, so the two stay interchangeable and the accountant's plain-text artifact never drifts from what the page shows.

type Transaction = {
  id: string           // stable; identifies the leaf as well as the row
  date: string         // YYYY-MM-DD
  account: string      // HSBC (debit) | HSBC (credit) | NatWest | Amex (credit)
  amount: string       // signed decimal, two places — never a JavaScript number
  description: string  // verbatim from the bank statement
  category: string
  source: string       // which statement it came from
}
Decision 4 — money is a decimal string, and arithmetic runs in integer pence. JavaScript numbers are IEEE-754 doubles. That is precisely the defect the spreadsheet carried: its 2023 total was stored as 2589.659999999998. Putting amount in a number would reintroduce, in new code, the bug the conversion just removed — and it would do so silently, in a system whose entire purpose is producing figures a tax authority relies on.

5 · The commitment

Committing a period is four steps, and each one has to be reproducible by someone holding only the data and this document.

1. Canonicalise. Each transaction serialises to a fixed-field-order byte string with no whitespace or encoding latitude. Two implementations must agree byte-for-byte or the root is worthless.
2. Hash. Leaf is the SHA-256 of that canonical form. Leaves sort by (date, id), so the tree is a function of the set, not of insertion order.
3. Build. Pairwise SHA-256 up to a single root.
4. Broadcast. One OP_FALSE OP_RETURN carrying a marker, the root, the period bounds and the transaction count.
Decision 5 — an odd node is carried up unchanged, never duplicated. The familiar Merkle construction duplicates a lone final node to complete a level. That admits the well-known duplicate-leaf ambiguity, in which two different transaction sets produce an identical root — which would let a set be misrepresented as the committed one. Carrying the odd node up instead costs nothing to implement now and cannot be retrofitted later, because by then the roots are on chain and immutable. This is the single decision in the document with no second chance.

What goes in the output

Marker, version, period start and end, the root, and the count. The count matters: without it a proof verifier cannot detect a set that has had transactions removed from its tail.

6 · Selective disclosure

Given a transaction, the page exports an inclusion proof: the leaf, its Merkle path, the root, and the transaction identifier on chain. Anyone can verify that this one transaction was in the set committed at that time, without learning anything about the others.

That is the piece that carries into Scripted Supply unchanged. A buyer proving a single purchase order to a financier, a supplier proving one delivery attestation in a dispute, and Henceforth Bitcoin Limited proving one transaction to an inspector are the same operation over the same code.

7 · What happens to the CSV

Upstash becomes the working store. transactions.csv becomes an export, regenerated on demand, and check.py and summarise.py keep working against it unchanged. One source of truth, one derived artifact, no divergence. The accountant continues to receive plain text.

The existing xlsx_to_csv.py already refuses to overwrite the ledger without --force; the same guard reasoning applies to the export path, which must never overwrite an export that contains rows the store does not.

8 · Error handling

ConditionBehaviour
A transaction fails validationThe period refuses to commit. Same rules as check.py: date is YYYY-MM-DD, amount is a signed two-place figure, description is non-empty.
Broadcast fails or is rejectedNo commitment record is written. A transaction identifier is stored only after the broadcast is accepted, never optimistically.
Period already committedRefused unless explicitly superseding, and a supersede chains to the previous root so an amendment is visible rather than silent.
Archive key unfundedThe existing message from the print-edition path, which already distinguishes an unfunded key from change still propagating.
Period contains no transactionsRefused. An empty root is a claim about nothing and would be indistinguishable from an unrecorded period.

9 · Testing

Behaviour is not shipped until it is asserted. Repository convention is vitest beside the module, following src/lib/*.test.ts.

  • Canonicalisation is stable — the same record produces the same bytes across runs and field orderings.
  • The root is a function of the set — shuffling insertion order does not change it.
  • Inclusion proofs verify — every leaf in a fixture set proves against the root.
  • Tampering fails — altering one amount by one penny invalidates that leaf's proof.
  • The duplicate-leaf attack cannot forge a root — the classic odd-node collision is constructed explicitly and must produce distinct roots.
  • Penny arithmetic — period totals computed from fixtures match the figures already filed: £586.43 to 31 January 2023, £2,596.67 to 31 January 2024, £526.27 for the eleven-month period to 31 December 2024.
  • No test spends — broadcast is exercised only through the fake-output dry-run path that render-pdf.mjs already provides.

10 · Out of scope

Named so they are not smuggled in: multiple companies or tenants; double-entry or triple-entry bookkeeping, this being a cash ledger; delivery-versus-payment contracts; the zero-install supplier portal; X12 and EDIFACT translation; any Forth contract compilation. This spec builds a ledger and a commitment primitive, and stops.

11 · Build order

Decision 6 — the entry form ships before the commitment. The accounts for the year ended 31 December 2025 are due around 30 September 2026, and roughly twelve months of transactions are untyped: the ledger's last entry is 2025-07-03, HSBC statements end May 2025, NatWest June 2025, and the Amex folder is empty despite an Amex purchase recorded in February 2025. Cryptography does not file accounts. The entry surface is what unblocks the filing, so it goes first and the commitment follows.
