# calendar-sync

Writes the week plan into an Apple Calendar named "Morning Board", so the plan
reaches the phone through iCloud.

    swift run --package-path scripts/board/calendar-sync calendar-sync

Run it from the repository root: it reads the store credentials from .env.local
in the working directory. Calendar access is granted once, interactively, on the
first run.

The sync owns the "Morning Board" calendar completely and touches no other
calendar. Running it twice changes nothing the second time. An empty read is
treated as an error rather than an instruction to empty the calendar, and so is
a partial one: if any plan day carries a date the tool cannot read, it names the
day and exits without touching the calendar, because a day quietly dropped would
take its existing event down with it.

    swift test --package-path scripts/board/calendar-sync

## If the editor reports errors that the build does not

You may see the editor flag "No such module 'CalendarSyncCore'" in
Sources/calendar-sync/main.swift, or "Cannot find type 'PlannedDay' in scope"
in the library sources, while `swift build` and `swift test` both succeed.

That is a workspace-resolution problem, not a code problem, and here is the
whole of it: this is a Swift package nested inside a JavaScript repository.
The editor's language server roots itself at the repository top level, sees a
JavaScript project, and never walks down to this Package.swift, so it cannot
resolve the module graph for files underneath it.

Two things are worth knowing before you spend time on it:

The three sibling application repositories solve the same class of problem with
a `buildServer.json` generated by `xcode-build-server`. That tool is not
available here — it binds an Xcode workspace or project, and this is a bare
Swift package with neither.

The build is the source of truth. Verify with the commands above rather than
the editor. A clean-room rebuild was confirmed on 2026-07-20: with every build
artifact removed, `swift build` succeeded and all 26 tests passed, while the
editor continued to report the same errors.

The practical fix, if the diagnostics bother you, is to open this directory as
its own editor workspace, where the language server finds Package.swift
immediately and resolves everything. Restarting the language server after the
first build also helps where it has cached a workspace from before this package
existed.
